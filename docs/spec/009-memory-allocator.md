# 009：會回收的記憶體配置器

狀態：**READY**
日期：2026-09-06
起因：智冠《三國演義》(1991) `AA.EXE` 的解壓階段

## 1. 問題

`AH=48h`（配置）是單向的 bump 配置器，`AH=49h`（釋放）是**空操作**
（原註解：「收下就好，不做回收」）。

配置過的段永遠不還，所以任何「配置 → 用 → 釋放 → 再配置」的迴圈
都會單調地把 640 KB 吃光。

### 量到的後果

`AA.EXE` 答完裝置選單、印出解壓提示之後：

| 服務 | 次數 |
|---|---|
| `AH=4Ah` 調整區塊 | 19,846 |
| `AH=48h` 配置 | 9,925 |
| `AH=49h` 釋放 | 9,921 |

九千多次配置、九千多次釋放，淨值只有 4 個區塊。但釋放不回收，
於是第 N 次配置之後 `freeSeg` 撞到 `MemTop`，`AH=48h` 開始回
「記憶體不足」，程式**以離開碼 255 結束**。

算術也吻合：可配置空間約 23,800 段，每次配置至少 2 段（含 MCB），
約九千多次就用完。

⚠ 這個失敗**沒有錯誤訊息**。主控台最後一行是解壓提示，然後就沒了。
從外面看像「跑到一半掛了」，而真正的原因在工具這邊。

## 2. 決定

改成**有 free list 的首次適配（first-fit）配置器**，涵蓋
`[FreeSeg, MemTop)` 這段。

| 服務 | 行為 |
|---|---|
| `AH=48h` | 首次適配；找到夠大的自由區塊就切一塊出來，剩下的留著。找不到時回 `AX=8`、`BX=` 最大可用，並設 CF |
| `AH=49h` | 標記為自由，**並與前後相鄰的自由區塊合併** |
| `AH=4Ah` | 縮小一律成功（切出後半段並標為自由）；放大只在後一塊是自由且夠大時成功，否則回 `BX=` 實際可達大小並設 CF |

合併是必要的，不是優化：不合併的話九千次配置／釋放會把空間切成
九千個碎片，最後一樣配不出大塊——換一種方式撞同一面牆。

### 保留 `AH=4Ah` 的 PSP 特例

原本的 `setBlock` 對 `ES == PSPSeg` 有特別處理，而且註解記著理由：
程式用「先要 `0FFFFh` 段、預期失敗、再用回報的大小要一次」來探測記憶體，
一律清 CF 報成功會讓它第一次呼叫就掉進錯誤路徑。

**那個行為要保住。** 這一版只換底層的配置策略，不動那個探測協定。

## 3. MCB 的忠實度

DOS 真的在每個區塊前面放一個 MCB（`M`／`Z` 簽章、擁有者、大小），
而且有些程式會走訪 MCB 鏈。

**這一版不做真正的 MCB 鏈**，維持原本「+1 段給假的 MCB」的做法，
只是改成由配置器統一管理。理由是範圍控制：目前沒有任何觀測到的程式
走訪 MCB 鏈，先做會用到的部分。

要走訪 MCB 的程式出現時，probe 會以「讀 `AH=52h` 之後掃記憶體」的形狀
浮現出來，那時再補。

## 4. 驗收

1. 一個配置／釋放交替數千次的迴圈**不應該**耗盡記憶體。
2. `AA.EXE` 答完裝置選單後**不再**以離開碼 255 結束在解壓階段。
3. `rich2` 既有測試全綠——尤其 `AH=4Ah` 的記憶體探測協定不能變。

## 5. 這一版沒解決的

- 真正的 MCB 鏈（§3）。
- `AH=4Bh`（EXEC）與子程序的記憶體歸屬。
- UMB／HMA。
