# 009：會回收的記憶體配置器

狀態：**READY**
日期：2026-09-06
起因：智冠《三國演義》(1991) `AA.EXE` 的解壓階段

## 1. 問題

`AH=48h`（配置）是單向的 bump 配置器，`AH=49h`（釋放）是**空操作**
（原註解：「收下就好，不做回收」）。

配置過的段永遠不還，所以任何「配置 → 用 → 釋放 → 再配置」的迴圈
都會單調地把 640 KB 吃光。

### 量到的後果

`AA.EXE` 答完裝置選單、印出解壓提示之後：

| 服務 | 次數 |
|---|---|
| `AH=4Ah` 調整區塊 | 19,846 |
| `AH=48h` 配置 | 9,925 |
| `AH=49h` 釋放 | 9,921 |

九千多次配置、九千多次釋放，淨值只有 4 個區塊。但釋放不回收，
於是第 N 次配置之後 `freeSeg` 撞到 `MemTop`，`AH=48h` 開始回
「記憶體不足」，程式**以離開碼 255 結束**。

算術也吻合：可配置空間約 23,800 段，每次配置至少 2 段（含 MCB），
約九千多次就用完。

⚠ 這個失敗**沒有錯誤訊息**。主控台最後一行是解壓提示，然後就沒了。
從外面看像「跑到一半掛了」，而真正的原因在工具這邊。

## 2. 決定

改成**有 free list 的首次適配（first-fit）配置器**，涵蓋
`[FreeSeg, MemTop)` 這段。

| 服務 | 行為 |
|---|---|
| `AH=48h` | 首次適配；找到夠大的自由區塊就切一塊出來，剩下的留著。找不到時回 `AX=8`、`BX=` 最大可用，並設 CF |
| `AH=49h` | 標記為自由，**並與前後相鄰的自由區塊合併** |
| `AH=4Ah` | 縮小一律成功（切出後半段並標為自由）；放大只在後一塊是自由且夠大時成功，否則回 `BX=` 實際可達大小並設 CF |

合併是必要的，不是優化：不合併的話九千次配置／釋放會把空間切成
九千個碎片，最後一樣配不出大塊——換一種方式撞同一面牆。

### 保留 `AH=4Ah` 的 PSP 特例

原本的 `setBlock` 對 `ES == PSPSeg` 有特別處理，而且註解記著理由：
程式用「先要 `0FFFFh` 段、預期失敗、再用回報的大小要一次」來探測記憶體，
一律清 CF 報成功會讓它第一次呼叫就掉進錯誤路徑。

**那個行為要保住。** 這一版只換底層的配置策略，不動那個探測協定。

## 3. MCB 的忠實度

配置器的狀態要發布成客體記憶體裡的 MCB 鏈，規格在 `docs/spec/012`。
`AH=48h`／`49h`／`4Ah` 之後立刻同步。

## 4. 驗收

1. 一個配置／釋放交替數千次的迴圈**不應該**耗盡記憶體。
2. `AA.EXE` 答完裝置選單後**不再**以離開碼 255 結束在解壓階段。
3. `rich2` 既有測試全綠——尤其 `AH=4Ah` 的記憶體探測協定不能變。
4. 走 MCB 鏈的程式看到的地圖與配置器一致（`docs/spec/012` §3）。

## 5. 這一版沒解決的

- `AH=4Bh AL=00`（EXEC 子程序）與子程序的記憶體歸屬。
- UMB／HMA。
- `AH=58h` 的配置策略。

## 附錄：`AH=4Ah` 的 `freeSeg` 只升不降（同日修正）

第一版寫成 `if blk+want+1 > d.freeSeg`，只在變大時更新可配置區起點。
那讓記憶體探測變成單向的災難：程式先要 `want=9EFFh` 探上限，
`freeSeg` 被推到 `A000h` ＝ 可配置區歸零；接著程式縮回真正要的大小，
`freeSeg` 卻留在 `A000h`。

DOS 的語意是「區塊邊界移到這裡」，升降都算，所以改成無條件設定。

⚠ **這個修正沒有改變智冠《三國演義》的症狀**（指令數與失敗位址完全相同）。
它是一個獨立存在的正確性問題，不是那個症狀的成因——
記在這裡是為了不讓下一個人把兩件事連在一起。

## 附錄二：`AH=4Ah` 縮小 PSP 區塊時，arena 要跟著往下長（同日修正）

只更新 `freeSeg` 是不夠的。程式把自己的 PSP 區塊縮小之後 `freeSeg` 確實降了，
但 arena 還停在舊的基底——**`[新 freeSeg, 舊基底)` 這段新釋出的記憶體
從來沒有進到區塊表裡**。

量到的狀態（修正前）：

```
freeSeg=23EF  arena=3 塊，零個自由區塊
  seg=5250 已配置
  seg=5291 已配置
  seg=9FFA 已配置
```

arena 是在 `freeSeg≈5250` 時建的，涵蓋 `5250..9FFF` 且全被配走。
程式接著縮小自己的區塊、`freeSeg` 降到 `23EF`，但那 190 KB 沒有被記錄。

**症狀離現場很遠**：智冠《三國演義》的 overlay 解壓後向 `AH=48h` 要
**3 個段**（48 bytes，環境指標陣列），配置失敗，MSC 啟動碼因此印
`R6009 - not enough space for environment` 並以離開碼 255 結束。
從外面看像「overlay 壞了」，實際上是配置器少記了 190 KB。

修法是 `setPSPBlock`：縮小時把 `[新 freeSeg, 舊基底)` 當成自由區塊接到最前面
再合併；放大時**只吃前端自由的部分**——已經配出去的區塊不能收回，
那會讓別人手上的指標失效。

修正後 `AA.EXE` 走過 overlay 啟動、開了五個檔（`DATA0.GRP`，
以及 `DATA1` 的 `.IDX`／`.NAM`／`.GRP` 三件套），離開碼從 255 變成 1，
錯誤也換成遊戲自己的（`ErrMsg: TITFONT.IMG  ErrNo: 888`）。

## 附錄三：`AH=4Ah` 放大 PSP 區塊時**不**檢查已配置區塊（刻意）

比較接近 DOS 語意的做法是：放大時的上限取「第一個已配置區塊的起點」，
因為那塊是別人的，長不過去。試過，**結果讓目標程式更早死**：

| | 寬鬆（現行）| 檢查 arena |
|---|---|---|
| 智冠《三國演義》走到 | 9,198,702 道指令，開 5 個檔 | 7,888,959 道指令，開 1 個檔 |
| 停在 | 遊戲自己的 `ErrNo 888` | `R6005 - not enough memory on exec` |

檢查版讓探測回報上限 `5150h`，程式當場判定記憶體不足、
**連 `AH=4Bh` 都沒發出**就放棄。

**兩種行為哪一個是真 DOS，目前沒有證據。** 要拿 DOSBox-X 當交叉 oracle
量一次：程式的 PSP 區塊後面卡著一塊 310 KB 的 far heap 時，
`AH=4Ah` 要求長到 `9EFFh` 會怎麼回。

在那之前保留寬鬆做法——它讓目標程式走得更遠，而走得更遠才有更多
可觀測的東西。**這是刻意的取捨，不是疏漏**，程式碼裡也標了。

⚠ 順帶一提，那次嘗試被既有測試 `TestSetBlockProbeMustFailFirst` 抓到一個
off-by-one：PSP 區塊從 `blk` 起算，**沒有**額外的 MCB 段要扣。多減 1 的話，
程式拿 DOS 自己回報的上限再要一次會失敗，而呼叫端的 `jb 錯誤` 會把那
判定成真的錯誤。那個測試存在的理由就是擋這個。

## 附錄四：智冠《三國演義》的記憶體問題，根因是沒發布 MCB 鏈

原版連續三次撞在記憶體上：`R6009 - not enough space for environment`、
`ErrMsg: TITFONT.IMG ErrNo: 888`（要 `0x94B` 段、最大自由 `0x507` 段）、
`DATA5.GRP` 那一層印完「程式載入中 請稍待」以 255 離開。三次的共同點是
配置器裡有 300 KB 以上被「已經用不到的東西」佔著。

根因是**配置器的狀態只活在 Go 這一側**。載入時建的那條鏈寫死兩格
（`PSPSeg−1` 大小 `0x2000`、`PSPSeg+0x2000` 一格鏈尾），之後不論配置器
怎麼變都不更新，而原版做兩件事都靠走這條鏈：

- **釋放**：沿鏈找自己的區塊逐一 `AH=49h`（`06DD:32C3`、`0583:3215`）。
  鏈是死的，它找不到，所以一塊都沒還——**看起來像「這個程式從不釋放」**。
- **算可用量**：從自己的 PSP 沿鏈加到鏈尾，把段數傳給載入函式
  （`0583:3068`，反組譯見 `docs/spec/012` §2）。鏈是死的，它拿到 `0x2000`
  ＝ 128 KB，而 `DATA5.GRP` 要 142 KB，於是判定載不下。

發布真正的鏈之後（`docs/spec/012`），同一份輸入：

| | 修正前 | 修正後 |
|---|---|---|
| 走到 | 250,037,578 道指令 | **280,760,793 道** |
| 離開碼 | 255（無訊息）| 1（程式自己的 `ErrMsg: File #1  ErrNo: 9`）|
| `AH=49h` 釋放 | **0 次** | 10 次 |
| 開過的檔 | 6 個，最遠 `DATA5.GRP` | **16 個，含 `DATA2.IDX`／`DATA2.NAM`／`DATA3.*`／`DATA2.GRP`** |
| 診斷開關 | 一定要開才走得到標題畫面 | **不需要**（開與不開結果相同）|

`DOSGOLEM_FREE_ON_OVERLAY` 已經移除。

### 已被推翻的斷言

| 斷言 | 當時的根據 | 實際 |
|---|---|---|
| 「這個程式從不釋放記憶體」 | 整趟 `AH=48h` 13 次、`AH=49h` 0 次 | 它一直在嘗試釋放，只是沿著一條死鏈找不到自己的區塊。**服務呼叫次數量到的是「程式做到了什麼」，不是「程式想做什麼」** |
| 「`DATA5.GRP` 那一層是記憶體數量不夠」 | 程式要 `0xFFFF` 段、拿到 122 KB 就收工 | `AH=48h BX=FFFF` 是走鏈的**起點**不是請求本身；`cmp al,7` 說明它只在意「鏈壞了沒」。失敗數字是鏈算出來的，不是配置器回的 |
| 「`TITFONT.IMG` 是記憶體數量問題，診斷開關已證明」 | 開關一開就走到標題畫面 | 開關把症狀補掉了，所以看起來像數量問題。數量會不夠是因為前一個程式沒能釋放，而那是同一個根因 |

**一個開關能讓症狀消失，不代表它指到了成因。** 診斷開關做的事
（強制標成自由）恰好與真正缺的機制（讓程式自己找得到區塊去釋放）
產生相同的可觀測結果，於是它同時證實了症狀、掩蓋了成因。
要分辨這兩者，得問「程式**打算**做什麼」——看它呼叫失敗前讀了哪些記憶體，
而不只看它呼叫了什麼。

## 附錄五：兩個差一段（2026-09-10，FTL《Dungeon Master》DOS 版）

狀態：**READY**（已實作並驗收）
起因：`dm.exe` 答完三個裝置選單後 `AH=4Ch` 離開碼 1，畫面停在文字模式。

### 量到的

`cmd/probe -exe dm.exe -type '111' -trace 120` 拍到：

```
#718425  AH=4A 要 0x9EFB 段  成功        ← 程式把自己的區塊擴張到約 651 KB
#718440  AX=4808                        ← int 21h AH=48（配置）
#718441  AX=4808 BX=0003                ← 只要 3 段（48 bytes）
#718442  AX=0008 BX=0002                ← 回錯誤碼 8、最大可用剩 2 段
#718449  進 sub_11789  AX=0008          ← Borland 的「DOS 錯誤碼轉 errno」
#718462  SI=0008                        ← errno ← 8
```

⚠ **Borland 的 `errno 8` 是 `ENOEXEC`，而 DOS 的錯誤碼 8 是「記憶體不足」，
兩者只是撞號。** 表面症狀看起來像「執行格式錯誤」，而被 spawn 的 `VGA`
確實是合法 MZ（`4d5a` 開頭、`LZ91` 簽章）——如果在「errno=8 → 查 C 的 errno 表」
就停下來，會得到一個自洽但方向全錯的結論。要追到寫入點才分得出來。

### 兩個根因

**一、`machine.MemTop` 是 `0x9FFF`。** 640 KB ＝ `0xA0000` 位元組 ＝ 段 `0xA000`，
與 `VideoSeg` 接在一起。`availFrom` 與 `initArena` 都把它當「上緣（不含）」用，
所以各少算一段。同一個 package 的 `dpmi.go` 寫的是 `dosMemTop = 0xa0000`，
兩處對 640 KB 的表示本來就不一致。

**二、`setBlock` 裡的 `setPSPBlock(blk + want + 1)` 多加了 1。**
`setPSPBlock` 的參數是**下一個 MCB 的位置**（它用 `size = base - newFree - 1`，
扣掉的那一段就是 MCB）。PSP 區塊的資料到 `blk+want-1`，下一個 MCB 就在
`blk+want`。

⚠ **只修其中一個沒有用。** 只改 `MemTop`，Borland 的 runtime 會跟著多要一段
（`AH=4A` 從 `0x9EFB` 變成 `0x9EFC`），剩餘還是 2——它固定留 4 段給自己，
所以上限往上一段，需求就往上一段。兩個一起修才有效。

### 依據

DOSBox-X `src/dos/dos_memory.cpp`：

- `DOS_AllocateMemory`：`block_size == *blocks` 時**整塊給出去、不另外切 MCB**，
  所以「剛好夠」就該成功。`dosgolem` 的 `splitBlock`（`b.size >= want+2` 才切）
  語意相同，不必改。
- `DOS_ResizeMemory`：放大時只併**緊接在後面那一個** MCB，且必須是 `MCB_FREE`
  （`total += mcb_next.GetSize()+1`）；失敗時仍 `mcb.SetSize(total)` 調到最大、
  `*blocks=total` 回報最大值、設 `DOSERR_INSUFFICIENT_MEMORY`。
  這一條與附錄三的「刻意不檢查已配置區塊」有出入，但**本輪不動**——
  附錄三記著改動會讓智冠《三國演義》更早死，而那需要另外一輪對拍。

### 驗收

- `tools/go.sh test ./...` 全綠（四個 app 的既有測試都沒有回歸）。
- `dm.exe` 從「718,783 道指令後離開碼 1」變成**跑滿 3 億道指令仍存活**，
  視訊模式從 `03h`（文字）進到 `13h`，`A0000` 有 16,647 個非零像素，
  開過的檔一路走到 `swoosh`／`anim`／`title`／`selector`／`FIRES`。
- `-dump-vram` 取出的畫面是《Dungeon Master》的標題（黃色 Dungeon ＋ 紅色 Master）。
