# 008 — 跑《臥龍傳》還缺的服務

日期：2026-09-05
狀態：**READY**

---

## 1. 現況：跑得動，但在第一個字倒下

把松崗 DOS/V 版的 `KI.EXE` 直接餵進 `cmd/probe`，**不必改任何程式碼**
就跑了 3,306,474 道指令、開了 14 個原版資料檔
（`GAMEPAL.BRG`／`TALK.DAT`／`ICONGRF.DAT`／`SOUND.DAT`／`MMAP.MAP`／
`MMAP.MDL`／`MMAP.MCH`／`BGM.DAT`／`SINARIO.DAT`），
設好 mode 12h，寫過 `3C0`／`3C4`／`3C5`／`3C8`／`3C9`／`3CE`／`3CF`。

然後它 `int 21h AH=4Ch` 帶著離開碼 8 停下來。

**離開碼 8 是 DOS 的「記憶體不足」**，但真正的原因不是記憶體：

```
#3306441 0110:F787   ; and ch,ch
#3306442 0110:F789   ; call far 0000:0000  ← 全形字型向量，沒被填過
#3306443 0110:0100   ; ← 掉進 sub_100DF 的中段
…
#3306464 0110:013B   ; int 21h AH=48h 失敗 → AX=0008
#3306473 0110:0153   ; int 21h AH=4Ch
```

`KI.EXE` 開機時向 `INT 15h AH=50h`（DOS/V 字型服務）要兩個遠位址，
把它們 patch 進單字元 blitter 裡的兩條 `call far 0000:0000`。
服務不存在 → 向量停在 `0000:0000` → **第一次畫字就是一次遠呼叫到零位址**。
落點恰好是開機配置記憶體的那一段，於是它重跑一次配置、失敗、報記憶體不足。

> 這是「錯誤訊息指向錯的地方」的標準形狀。離開碼、訊息、最後的
> `int 21h` 全部一致地指向記憶體，而根因在 200 萬道指令之前的一個空指標。
> **沒有指令軌跡的話這一題查不出來**——`-trace` 是這次唯一有用的證據。

臥龍傳專案 `docs/re/29` 已經把整條鏈靜態解完（字型服務、`STR.EXE`、
索引式、資料檔），所以這裡不必再逆一次，照著接就好。

## 2. 沒實作的服務清單（實測）

| 服務 | 次數 | 處置 |
|---|---:|---|
| `int 15h AH=50h AL=00` | 2 | **必須實作**（§3）。不做的話跑不出任何畫面 |
| `int 33h AX=000Ch` 設事件處理常式 | 2 | 收下並記住向量，不呼叫（§5）|
| `int 33h AX=000Fh` 設 mickey/pixel 比例 | 2 | 收下就好 |
| `int 21h AH=51h` 取 PSP | 1 | 回 `BX = PSPSeg`。**這是程式的第一道指令**（§4）|
| `int 1Ah AH=02h` 取 RTC 時刻 | 1 | 回固定時刻，與 `int 21h AH=2Ch` 同一份（§4）|
| `int 61h` AH=00/02/03/06/07/08/0C | 各 1 | 記錄後回成功（§6）|

## 3. `INT 15h AH=50h`：字型服務

### 3.1 呼叫端要什麼

`KI.EXE` 的 `sub_1F720` 發兩次：

| | BX | DX | 存到 |
|---|---|---|---|
| 半形 | `0000h`（BH=0）| `0810h`（8×16）| `cs:1F791`（offset）／`cs:1F793`（segment）|
| 全形 | `0100h`（BH=1）| `1010h`（16×16）| `cs:1F78A`／`cs:1F78C` |

回傳 `ES:BX` ＝ 取字模常式的遠位址、`AH=0`、`CF=0`。
`jb` 之後**不設任何預設值**，所以 `CF=1` 與沒實作是同一個結果。

取字模常式被 `call far` 呼叫時：`CX` ＝ Big5 字碼（`CH` 高位元組、`CL` 低位元組），
`ES:SI` ＝ 呼叫端在堆疊上開的 32 byte 緩衝區。回傳 `AX=0`。

### 3.2 怎麼實作

在 `StubSeg` 種兩段三個 byte 的 real mode stub：

```
StubSeg:fontFullOff  CD F1 CB     ; int F1h ; retf
StubSeg:fontHalfOff  CD F2 CB     ; int F2h ; retf
```

`int F1h`／`F2h` 由服務層接手（向量表預設就指著 `StubSeg`，
`DOS.handle` 的「程式自己裝了處理常式就讓開」規則照樣成立）。
兩支 handler 做的事與 `STR.EXE` 的常駐常式一樣，只是不經 DOS 檔案呼叫：

**全形**（`STR.EXE` 常駐段 `+5D`，bytes 逐條解過）：

```
ch < A4h  → n = (ch − A1h) × 9Dh
ch < C9h  → n = (ch − A4h) × 9Dh + 198h
ch < FAh  → n = (ch − C9h) × 9Dh + 16B1h
否則      → n = 56h，且**跳過底下的低位元組加法**
cl > 7Eh  → cl −= 22h
n += cl − 40h
讀 END_S13.DAT 的 [n×1Eh, +1Eh) 到 ES:SI，ES:SI+1Eh 填一個 word 0
```

**半形**（`+DF`）：`n = cl`，讀 `END_S14.DAT` 的 `[n×0Fh, +0Fh)`，
`ES:SI+0Fh` 填一個 byte 0。

⚠ **越界那一支是 `jmp` 到乘法之前，不是繼續往下加。**
`0x29F: mov ax,56h / jmp 0x2B3` ——`0x2B3` 已經在低位元組加法之後。
照文字敘述往下讀會得到「`0x56` ＋ 低位元組」，那是錯的，
而且錯出來的字模看起來仍然像個字。

### 3.3 為什麼用 `END_S13`／`END_S14`，不是 `STR.EXE` 寫死的檔名

`STR.EXE` 寫死的是 `END_S10.DAT`／`END_S11.DAT`，而封裝內的那兩個檔
是結局過場圖（臥龍傳專案 `docs/re/29` §6 未解）。真正符合規格的是
`END_S13.DAT`（408 格符號 ＋ 倚天 `stdfont.15`）與
`END_S14.DAT`（＝倚天 `ascfont.15`，byte-for-byte 相同）。

所以檔名做成**參數**（`oracle.Options.FontFull`／`FontHalf`），
預設 `END_S13.DAT`／`END_S14.DAT`。

⭐ **實驗做了**（[`docs/findings/004`](../findings/004-font-source-and-mouse-events.md) §3）：
用 `END_S10/S11` 跑，216 次取字模有 68 次超出檔尾，中文變成一片雜訊。
「照封裝內的檔案跑 `STR.EXE`」確定不成立。⚠ 但那不等於「`STR.EXE` 有 bug」
——安裝流程如果會改名，安裝後的目錄仍然可能是對的。

> **本專案不含任何字型資料。** 這兩個檔是玩家自備素材目錄裡的檔案，
> 服務層只是去讀它，跟 `int 21h AH=3Fh` 讀別的資料檔沒有差別。

## 4. `INT 21h AH=51h` 與 `INT 1Ah AH=02h`

`AH=51h`（取 PSP）是 `KI.EXE` 的**第一道指令**：

```asm
mov ah, 51h / int 21h / mov ds, bx / mov al, ds:80h
```

沒實作 → `BX` 是呼叫端留下的值 → `ds:80h` 讀到垃圾當成命令列長度。
處置：`BX = PSPSeg`，`AH=62h` 同樣。

`INT 1Ah AH=02h` 回 BCD 的時分秒。與 `int 21h AH=2Ch` 共用 `DOS.Now`，
**不要各給各的**——兩份不一致時亂數種子會跟著飄，而症狀是
「同一組輸入跑出不同畫面」。

## 5. `INT 33h`：兩個新功能與座標倍率

- `AX=000Ch`：設事件處理常式（`ES:DX` ＝ 常式、`CX` ＝ 事件遮罩）。
  **記下來但不呼叫。** 呼叫它要模擬真的中斷時序，而遊戲的主迴圈同時也
  在輪詢 `AX=3`（`sub_20070`），輪詢那條路徑已經夠用。
  ⚠ 記下來的理由是診斷：之後若出現「點了沒反應」，第一件要問的事就是
  「遊戲是不是只等事件不輪詢」。
- `AX=000Fh`：設 mickey/pixel 比例。收下就好。
- **`Mouse.XScale` 要能設。** 現在寫死 2（mode 13h 的 320 寬對 640 虛擬座標）。
  臥龍傳是 640×480 的 mode 12h，驅動的虛擬座標與像素 1:1，所以 `XScale = 1`。
  寫死 2 的話送出去的 X 全部差一倍，而畫面看起來只是「點不到東西」。

## 6. `INT 61h`：音源 TSR

`YNSOUND.COM` 常駐後把 `INT 61h` 指到自己，`AH` 是 command index
（臥龍傳專案 `docs/re/17`）。`KI.EXE` 開機走 `AH=00h`／`02h`／`03h`，
之後是 `06h`／`07h`（交出資源指標並初始化）、`08h`（停止）、`0Ch`（設回呼）。

**音源本身不模擬**：回 `AX=0`、`CF=0`，只記下哪個 command 被叫過。
理由是對拍比的是畫面，而音訊 parity 在臥龍傳專案那邊已經用錄音比過了
（`docs/spec/29-audio.md`）。

⚠ **`AH=0Ah` 回 flags 給 `AL`。** 回 0（＝沒有任何旗標）是安全的預設，
但要記在未實作清單裡，不要讓它安靜地變成「有旗標」。

### 6.1 ⭐ `AH=0Ch` 是例外：遊戲時鐘掛在這一支上

`AH=0Ch` 登記一支 far 回呼（`DS:DX`，`AL=1` 表示取消）。
驅動把 PIT ch0 的除數設成 `0x0100`（4660.87 Hz），自己分頻 16，
**以 291.30 Hz 呼叫遊戲登記的回呼**；再分頻 256 鏈回原本的 `INT 8`，
所以系統時鐘不會走鐘（臥龍傳專案 `docs/re/61` §3）。

遊戲那一側的回呼只有六條指令：設一個「這一輪有中斷來過」的旗標、
把一個飽和在 `0xFF` 的計數器加一。整個時間模型建在它上面——
戰略速度 `ds:0CFAh` 就是「一個子刻等幾個回呼」，
一個遊戲日 ＝ 24 時 × 9 子刻 ＝ 216 子刻。

> ⭐ **不接這一支的話遊戲時鐘不會走，而畫面完全正常。**
> 日期永遠停在第一天，兩層節流的等待迴圈也永遠等不到——
> 看起來像「遊戲在等玩家操作」，不像「少接了一支服務」。
> 實測：接之前跑四千萬道指令停在 `196年4月1日 1時`；接之後同一個位置是
> `12時`，之後每五百萬道指令推進一個遊戲日。

實作：機器層提供「每 n 道指令遠呼叫一次」
（`Machine.SetPeriodicFarCall`），`n = IRQ0Every ÷ 16`。
16 有兩個來源——`291.30 ÷ 18.206` 與驅動裡 `cs:0B6Ah` 的分頻值。

兩件事要注意，反面都不會報錯：

1. **是遠呼叫不是中斷**：不推旗標、不清 IF。回呼是 `retf` 結尾的。
   推錯的話堆疊差兩個 byte，`retf` 回到一個**看起來合法**的位址。
2. **不看 IF**。真機上這是別人的 ISR 在 `cli` 之後才呼叫遊戲的回呼。
   掛在 IF 上的話初始化期間那一大段 `cli` 會把時鐘整個吃掉。

## 7. 怎麼驗

| 項目 | 驗收 |
|---|---|
| 字型索引式 | 單元測試：「一」`0xA440`、「國`0xB0EA`」、「龍」`0xC073` 三個字的格號，與臥龍傳專案 `docs/re/29` §5 記的「序號一律差 −408」對得上 |
| 越界 | `0xFA40` 之後的字碼一律回格號 `0x56`，**不加低位元組** |
| 半形 | `'A'`（`0x41`）→ 格號 65，讀 `END_S14.DAT` 的 `[975, 990)` |
| 接線 | 跑 `KI.EXE`：不再出現「離開碼 8」，`Unimplemented` 裡沒有 `int 15h AH=50` |
| 整體 | 跑到主畫面，`Planar()` 的 640×480 裁掉上下各 40 列與原版截圖逐點比 |
| 遊戲時鐘 | 登記回呼之後 `Machine.PeriodicCalls()` 要真的增加；取消之後要停。**0 次與「遊戲不看時鐘」長得一模一樣** |

⚠ **「不再崩潰」不是驗收。** 字模讀錯一個 byte 也不會崩潰，
只會畫出看起來像字的東西。驗收要落到逐點比對。
