# 012 — 鍵盤走 IRQ1、滑鼠虛擬座標倍率依模式決定

日期：2026-09-06
狀態：**READY**（§1 鍵盤 IRQ1、§2 滑鼠倍率、§3 多次點擊）
動機：`GIN3PS.EXE` 停在主選單的互動迴圈，但送鍵與點擊**完全沒有反應**，
而且沒有任何錯誤——畫面逐位元組不變（`~/cht/logh3/docs/re/08`）。
兩個獨立的原因：鍵盤只走 BIOS，滑鼠座標被固定倍率乘掉。
前置：[`004`](004-dos-bios-services.md)（int 16h／int 33h 的第一版）。

---

## 1. 鍵盤走 IRQ1（READY）

### 證據

| 事實 | 證據 | 等級 |
|---|---|---|
| 遊戲自己裝 `int 09h` 與 `int 16h` 處理常式 | probe 的 VecSets：`#23289884 int 09h ← 348A:0002`、`#23289841 int 16h ← 348A:006C` | confirmed |
| 只填 BIOS 緩衝區時，送鍵對畫面零影響 | 逐位元組比對 | confirmed |
| 送 IRQ1 之後，中斷確實進到遊戲的處理常式 | `鍵盤中斷送出 6 次` | confirmed |

### 語意

自己裝 `int 09h` 的程式從**埠 0x60** 讀掃描碼，BIOS 的鍵盤緩衝區對它完全
不存在。所以執行器要能送真的鍵盤中斷：

- `Machine.QueueScan` / `QueueKey` 把 set-1 掃描碼排進佇列。
  **按下與放開是兩個碼**（放開 ＝ 按下 `|0x80`），兩個都要送——只送按下的
  話，自己記按鍵狀態的程式會一直以為那個鍵還按著。
- `keyTick` 在每道指令後檢查：佇列非空、到了間隔、`IF` 開著、且 `int 09h`
  的向量不是我們的 stub 時，把掃描碼放進埠 0x60 並送 `int 09h`。
  中斷關著時**留著不丟**，與 IRQ0 同樣的理由。
- `In8(0x60)` 回目前的掃描碼。
- `Machine.KeyIRQs` 記實際送出的次數。**「送不出去」與「遊戲不理會」是
  兩件事**，沒有這個數字就分不開——本案就是靠它確定鍵有進去，
  問題不在鍵盤。

## 2. 滑鼠虛擬座標倍率依視訊模式決定（READY）

### 證據

| 事實 | 證據 | 等級 |
|---|---|---|
| 遊戲用 `int 33h AX=0005h`（取按下資料）偵測點擊，鏈內 149,037 次 | probe 的 int 33h 各功能統計 | confirmed |
| 倍率固定 2 時，選單上的點擊全部無效（畫面零變化）| 四個位置逐位元組比對 | confirmed |
| 改成依模式決定之後，同樣的點擊立刻改變畫面 | 960／1034／74 個像素 | confirmed |

### 語意

滑鼠驅動的虛擬座標系固定是 **640 寬**，所以 320 寬的模式回報出去的 X 是
像素的兩倍，640 寬的模式一比一。原本寫死 2，是照 mode 13h 的 rich2 定的。

改為：`Mouse.XScale == 0` 時依 `Machine.PixelWidth()` 決定
（320 寬 → 2、640 寬 → 1）；設非 0 就強制用那個值。

**這種錯不會報錯。** 點擊落在兩倍遠的地方，畫面完全正常，症狀只是
「點了沒反應」——看起來像遊戲卡住，而不像座標算錯。

## 3. 多次點擊（READY）

`-clicks "x,y,at[,hold]"`（分號分隔）讓一次執行可以送多個點擊。
原本只有單一 `-click-*`，而互動的驗證天生需要「先跳過開頭、再點選單」
這種兩段以上的序列。

## 驗收

- 單元測試 `TestMouseScaleFollowsVideoMode`（五個模式）、
  `TestMousePollIsRecorded`（mode 13h 仍是 2 倍）。
- 整合：原版鏈跑到主選單後點在選單上，畫面出現反白條；同一個點擊在
  修正前是零像素變化。
