# 010：`int 21h AH=4Bh AL=03` 載入 overlay

狀態：**部分完成**（載入器可用；載入之後的執行環境未解，見 §4.1）
日期：2026-09-06
起因：智冠《三國演義》(1991) `AA.EXE`

## 1. 為什麼需要

`AA.EXE` 答完裝置選單後呼叫 `AH=4Bh AL=03` 載入 `DATA0.GRP`。
沒實作的話程式 far call 進一片空白，然後在**幾百萬道指令之後**
死在一個與這裡毫無關聯的位址（量到 `CS:IP = EB14:7F00`）。

這也解釋了那款遊戲的 `DATA0`／`DATA4`／`DATA5.GRP` 為什麼開頭是 `MZ`：
它們是 **overlay 模組**，不是打包過的資料容器。

## 2. 已實作

`machine.LoadOverlay(data, loadSeg, relocFactor)`：

- 與 `LoadEXE` 的差別是**它什麼都不設**——不建 PSP、不動 `CS:IP`、不碰 `SS:SP`。
  overlay 是被 far call 進去的程式碼。
- 重定位套的是 `relocFactor`，**不是** `loadSeg`。DOS 讓呼叫端分別指定，
  多數程式給相同的值但不保證；混用會在兩者不同的程式上安靜地載入一份
  指向錯地方的映像。
- 載入失敗時把原因寫進 `Console` 並回 `AX=8`＋CF。
  **回成功而沒載進去**會讓程式 far call 進空白，症狀出現的位置與原因無關。

`DOS.Overlays` 記每一次成功的載入。**這是唯一的觀測點**——overlay 沒有 PSP、
不動 `CS:IP`，從暫存器與開檔清單都看不出它發生過。

## 3. `[HARD]` 診斷資料要在載入之前抄

參數區塊常常就落在 overlay 要載入的那一段。載完再讀，讀到的是剛寫進去的映像。

踩過一次：印出來的「參數區塊」是 `FC 06 1E 0E 8C C8`，
也就是 `CLD; PUSH ES; PUSH DS; PUSH CS; MOV AX,CS`——一段 overlay 進入碼。
看起來像「程式傳了機器碼當參數」，把人帶往完全錯的方向。

## 4. 載入段：程式是刻意的（已查明）

`AA.EXE` 的呼叫帶 `ES:BX = 0100:0100`，那個位址正好是 `LoadSeg:0000`
（映像起點），讀出來的載入段與重定位加數都是 `0110h` ＝ `LoadSeg` 本身。

一度以為那是「讀到重定位後的映像位元組」。**不是。** 逐位元組比對：

```
映像原本（檔案 0x5400）: 55 8b ec b8 04 00 9a 1a
執行期在同一位址讀到  : 10 01 10 01 04 00 9a 1a
```

**後四個 byte 相同，前四個被覆寫成 `10 01 10 01`。** 而且映像 offset 0
沒有任何重定位項（全檔 5,342 筆，一筆都不指向那裡），
所以那個值不可能是重定位的產物。

結論：程式**刻意**把參數區塊寫在自己的映像起點，並要求把 overlay
載到同一個地方。這是 **chain-load**——它用新模組覆蓋自己不再需要的那一段。

載入器照做是對的。

## 4.1 載入之後：overlay 的 C 啟動碼配置失敗（已定位）

overlay 載進去之後，程式以 `run-time error R6009 - not enough space for
environment` 結束，離開碼 255。

### 離開點是 MSC runtime 的 `exit()`

`0583:04B6`（在 overlay 內）。`DATA0.GRP` 是**打包過的執行檔**——
檔頭只有 2 段、1 筆重定位、內容高熵，靜態反組譯是亂碼。
用 probe 的 `-dump-mem` 從記憶體把解開後的碼取出來才看得到：

```
48e: push cs
48f: call 546
492: or  ax,ax  /  je 4a7
496: pop ax                  ; AX ← CS ＝ 0583，AH ＝ 05
497: or  ah,ah  /  jne 4a7   ; AH 非零 → 跳過下面那行
4a2: mov word [bp+6], 0FFh   ; ← 沒有執行到
4af: mov ax,[bp+6] / mov ah,4Ch / int 21h
```

**所以 255 不是 runtime 代入的，是呼叫端本來就傳 255**——
那正是 MSC 的 `_amsg_exit(9)`，對應 `R6009`。

### 根因：`__setenvp` 的配置失敗

`R6009` 由 MSC 啟動碼的 `__setenvp` 發出：它讀 `PSP:2Ch` 的環境段、
數字串、再配置指標陣列。配置不到就走這條。

所以問題**不在 overlay 載不進去**（它載進去了、啟動碼也跑起來了），
在 chain-load 之後的記憶體狀態不符合 overlay 啟動碼的預期。

已排除（都試過，指令數與失敗位址完全不變）：`AH=4Ah` 的 `freeSeg`
只升不降、`AH=43h`／`29h`／`67h` 未實作、裝置選單的六種組合
（第三題 Disk 是分岔點，前兩題不影響）。

### 已排除：DOS 服務改壞 `ES:BX`

一度懷疑某個服務回傳時動到不該動的暫存器，讓 `AH=4Bh` 拿到錯的參數區塊位址
（那種錯的症狀會出現在很後面的另一個呼叫上，很難追）。

加了 `DOS.CallTrace` 記每一次 `int 21h` 進入與離開時的 `ES:BX`，
**沒有任何一次被服務改動**。假說否定。

追蹤同時顯示 overlay 的 C runtime 是**乾淨地收尾**的：
`AH=40h` 印錯誤訊息 → `AH=25h` 逐一還原 `34h`–`3Eh` 的中斷向量
（那正是 MSC 浮點模擬器的向量範圍）→ `AH=4Ch AL=FF` 離開。
所以它不是崩潰，是啟動碼判定失敗後照正常路徑退出。

### 下一步

比對 MSC 6.0 啟動碼算堆積上限的方式與這裡的記憶體模型。可疑的兩處：

- `PSP+2`（記憶體上限）在 `AH=4Ah` 縮小區塊之後**沒有更新**。
  真 DOS 的行為要確認——如果它會更新，而啟動碼拿它算堆積，
  這裡就會算出一塊不存在的空間。
- chain-load 之後 PSP 仍是**父程式的**。overlay 的啟動碼假設 PSP
  描述的是自己，但那個 PSP 的區塊大小是父程式縮過的（`0x22EE` 段）。

兩者都要拿 DOSBox-X 當交叉 oracle 驗——這是 `CLAUDE.md` 規定的
第三位階，正是這種「我們的模型對不對」的問題該用它的時候。

## 5. 這一版沒解決的

- `AL=00h`（載入並執行子程序）：需要另一套 PSP 與返回機制，目前沒有程式用它。
- `AL=01h`（載入但不執行）。
- overlay 的記憶體歸屬：載入器不向配置器登記那塊空間。
