# 193 — 時序暫存器：從 CRTC 算掃描位置（預設不啟用）

前置：[`192-crtc-effects.md`](192-crtc-effects.md)（列距與分割畫面）、
[`190-irq0-calibration.md`](190-irq0-calibration.md)（機器速度的標定）

## 1. 定位

`0x3DA`（Input Status 1）現在是**行為模型**：拿讀取次數的 bit4 翻轉，
讓兩種等待迴圈都轉得出來。

```
in al,dx ; test al,8 ; jnz -5   ; 等這一次回掃結束
in al,dx ; test al,8 ; jz  -5   ; 等下一次回掃開始
```

那讓程式跑得下去，代價是**回掃的頻率是假的**——它由程式輪詢的快慢決定，
不由 CRTC 決定。程式拿回掃當時鐘量速度、或靠它算動畫節奏時，量到的是
自己的輪詢速度。

這份規格加上真的時序模型：從 CRTC 的時序暫存器算出一幀的形狀，再從
機器的指令數換算現在掃到哪一條線。

**預設不啟用。** 既有的對拍收據都建立在行為模型的 `in` 回傳序列上，
換掉會讓每一份都失效。要用的人開 `Machine.CRTCTiming`。

## 2. 時序怎麼算

三個輸入源，缺一不可：

| 來源 | 給什麼 |
|---|---|
| Misc Output（`3C2`）bit2–3 | 像素時鐘：`0` ＝ 25.175 MHz、其餘 ＝ 28.322 MHz |
| Sequencer clocking mode（`3C4`／`01`）bit0 | 一個字元幾個像素：`1` ＝ 8、`0` ＝ 9 |
| CRTC `00`／`06` ＋ overflow | 一條線幾個字元時鐘、一幀幾條線 |

修正項照 DOSBox 的 `vga_draw.cpp`（`VGA_SetupDrawing`）：

```
htotal = crtc[00] + 3 + 2      // VGA 專屬的 +3，再加共通的 +2
vtotal = (crtc[06] | overflow) + 2
```

驗算（VGA 的兩個標準模式，25.175 MHz、8 像素字元）：

| 模式 | `htotal` | `vtotal` | 水平 | 垂直 |
|---|---:|---:|---:|---:|
| `12h` 640×480 | 100 | 525 | 31.47 kHz | **59.94 Hz** |
| `13h` 320×200 | 100 | 449 | 31.47 kHz | **70.09 Hz** |

兩個都落在 VGA 的標準值上（31.5 kHz、59.94 Hz／70.09 Hz），公式可信。
59.94 而不是 60 是對的——VGA 的 480 線模式與 NTSC 同源。

### 各段的起訖

垂直方向的三個位置都是 10 位元，高位散在 overflow（`07`）裡——
**這是最容易只讀低 8 位的地方**：

| 位置 | 低 8 位 | 高位 |
|---|---|---|
| vertical total | `06` | overflow bit0、bit5 |
| vertical display end | `12` | overflow bit1、bit6 |
| vertical retrace start | `10` | overflow bit2、bit7 |
| vertical blank start | `15` | overflow bit3、max scan line（`09`）bit5 |

## 3. 從指令數換算到掃描位置

dosgolem 的時間由指令數驅動，機器速度是 `StepsPerSecond()`
（[`190`](190-irq0-calibration.md)）。所以：

```
一條線幾道指令 = StepsPerSecond / 水平頻率
現在在第幾條線 = (Steps / 每線指令數) mod vtotal
```

`0x3DA` 依這個位置回報：bit3 ＝ 在垂直回掃期間、bit0 ＝ 不在顯示區
（水平或垂直任一在空白期）。

⚠ **這仍然不是週期精確的。** 它把「機器速度」當成常數，而真機上一道
指令花多久隨指令而異（[`191`](191-two-clocks-relationship.md)：暫存器
運算 3.25 週期、繪圖 7.40）。所以回掃的**頻率**對得上 CRTC，
單一次讀取落在哪個位置則是近似。

## 4. 不做的部分

**逐掃描線的光柵重繪。** 程式在掃描中途改暫存器（改調色盤做漸層天空、
改顯示起點做分割捲動）時，畫面的上下半部用的是不同的暫存器值。要重現
那個，得記錄每一次暫存器寫入發生在哪一條線，然後解畫面時逐列回放。

那是另一個量級的工作，而且**它需要的正是這份規格提供的位置查詢**——
所以先做這一層。

**等有程式真的需要才做**，追蹤在 `docs/worklist.json` 的
`raster-per-scanline-replay`（`deferred` 層）。照著想像實作的話會做出
一套沒有案例驗證的回放機制，而它錯在哪要等第一個真正用到的程式才會
知道。判準寫在那一條的 `blocked_by`：有一款要對拍的程式，畫面對不上
而原因追到「它在掃描中途改了暫存器」。

## 5. 驗收

1. `12h` 與 `13h` 的 refresh rate 算出來是 59.94 Hz 與 70.09 Hz。
2. 三個垂直位置的高位元都算進去（overflow 的各個位元）。
3. `CRTCTiming` 關著時，`0x3DA` 的回傳序列與現在完全相同。
4. `CRTCTiming` 開著時，兩種等待迴圈都轉得出來，而且回掃的頻率與
   CRTC 算出來的一致。
5. 既有測試零修改全過。
