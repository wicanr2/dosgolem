
## 2.2 BIOS 計時器 stub 的還原順序（`int 08h` → `int 1Ch`）

`int 08h` 的預設處理是 StubSeg 裡一段真的程式碼（`machine.biosTimerOff`）。
它的**還原順序**要照 IBM PC BIOS 的 `TIMER_INT`：

```
push ds / push ax / push dx
mov ax,40h / mov ds,ax
inc word [6Ch] / jnz +4 / inc word [6Eh]
int 1Ch
pop dx / pop ax / pop ds
iret
```

**還原在 `int 1Ch` 之後，不是之前。** `int 1Ch` 的處理常式是應用程式掛的，
它弄髒 DS／AX／DX 都由 BIOS 這三個 `pop` 收拾。80186 之後常見的寫法是
`pusha`／`popa`，而**那兩道不含段暫存器**——掛 1Ch 的程式因此可以
理直氣壯地 `mov ds, 自己的段` 而不還原。

反面（在 `int 1Ch` 之前就 pop 完）沒有任何錯誤訊息：DS 漏回被中斷的
程式，它接著用錯的段讀資料，照樣一路執行下去。

> 實例（源平合戰 `MAIN.EXE`，2026-09-06）：它的 1Ch 是
> `cli / pusha / mov ds,2A1E … popa / sti / jmp far 舊向量`。DS 漏回
> 位元碼直譯器之後，直譯器改從 `2A1E:SI` 抓位元碼（原本是 `336E:SI`），
> 執行了四百道別的模組的位元碼，物件型別查表取到第 82 項（表只有 27 項），
> `DS` 變成 0，再過十九萬道指令才走進低位記憶體結束。
> **症狀離成因十九萬道遠，而且畫面停在一個正常的對話框上。**
> 修好之後遊戲跑進主選單並開始輪詢滑鼠。

## 4.1 int 33h 的水平座標倍率隨模式而變

int 33h 的虛擬螢幕**永遠是 640 格寬**，不管實際模式多寬：320 寬的模式
（13h）回報值是像素的兩倍，所以 X 永遠是偶數；640 寬的模式（12h）一比一。

寫死 2 的話，640 寬畫面上點右半邊會回報成超出畫面的座標。遊戲判定
「不在任何按鈕上」而**安靜地什麼都不做**——沒有錯誤，畫面就是沒反應。

## 4.2 點擊要落在程式真的在輪詢的視窗裡

`cmd/probe -clicks "步數:X:Y,…"` 一次帶整串輸入，`-click-hold` 是按住的
指令數。挑步數之前先看報告裡的**輪詢分佈**：程式重畫畫面時可以兩千萬道
指令一次都不問滑鼠，點在那段等於沒點。

> 源平合戰 `MAIN.EXE` 從 TSR 常駐算起：#20M 點掉磁片提示，之後
> #23M–#60M 完全不輪詢（在畫主選單），#60M 之後才收得到主選單的點擊。

## 4.3 一次跑存好幾張畫面

`cmd/probe -shots "步數:路徑,…"` 在指定步數各存一張畫面色號（色盤存成
同名 `.pal`）。**要看中途的畫面不要重跑**——走到遊戲深處的畫面動輒
好幾億道指令，一次跑五分鐘，為了看中間一張再跑一次是純粹的浪費。

## 4.4 按鍵要在程式開始輪詢之後才送

`cmd/probe -keys` 是**一開始就排進佇列**，程式還沒開始輪詢就被吃掉了。
要在特定畫面送按鍵用 `-keys-at "步數:字串,…"`。

## 4.5 按住的長度要用「輪詢次數」算，不是指令數

`-click-hold` 是固定指令數，**在不同畫面之間不可移植**。同一支遊戲的
輪詢頻率可以差三個數量級：

> 源平合戰 `MAIN.EXE`：磁片提示每千萬道指令只問 12 次滑鼠（約 83 萬道
> 一次），讀檔選單每千萬道問一千次以上（約 1 萬道一次）。三百萬道的
> 按住在前者剛好夠一次，在後者會被讀成四千次連點——按下選單第二列
> 之後那四千次繼續打在下一個畫面上，遊戲以離開碼 255 結束，
> 看起來像「點那一列會讓遊戲關掉」。

`-click-polls N` 改成**按住到程式真的讀了 N 次滑鼠才放開**。預設用 3。
判準與畫面無關，寫死的步數則要每個畫面重調一次。

## 4.6 找「控制流在哪裡分岔」：`-ip-log`

`-ip-log 起:迄:路徑` 把那一段每一道指令的 `CS:IP` 以二進位寫出來
（每筆 4 bytes）。跑兩次只差一個輸入的執行，再拿 `cmp` 找第一個不同的
位元組，就是控制流第一次分岔的位置。

三百萬道指令的完整暫存器軌跡是三百 MB 的文字，同一段只記 `CS:IP` 是
12 MB；**先用它定位，再用 `-trace` 對那一小段抓暫存器**。

> 用法（源平合戰的設定畫面）：一次點在會回應的選項框、一次點在按不動的
> 「決定」鈕，其餘完全相同。兩份 `CS:IP` 在點擊後 8467 道分岔，位置是
> `336E:2A10`——一支 `pointInRect(x, y, x0, y0, x1, y1)` 的遠呼叫。
> 之後只要把它的參數印出來，畫面上註冊了哪些矩形就一覽無遺。

## 4.7 看「程式在比什麼」：`-call-args`

`-call-args CS:IP:字數:起:迄` 每次執行到那個進入點就把堆疊上的參數印出來。
位置取**進入點**（還沒 `push bp`），所以參數從 `SS:SP+4` 起算——遠呼叫的
返回位址佔 4 bytes。

控制流只告訴你「沒中」，參數才告訴你「拿什麼去比」。

## 4.8 記錄除以零的現場

C runtime 遇到除以零只印一句 `run-time error R6003` 就走人，離開碼 255，
**現場什麼都不留**。`cpu.CPU.DivErrors` 記下每一次除以零當下的 `CS:IP`
（最多 32 筆），probe 的報告會印出來。位址是**下一道**指令——8086 推的
返回位址指向下一道。

## 4.9 監看與讀檔紀錄都保留「最後」而不是「最前」

`-watch` 的寫入紀錄與讀檔紀錄都改成留最後幾筆。要找的通常是「誰最後
把它寫壞的」；砍後面那版會在開機階段就把配額用光，真正的兇手一筆都不留。

## 4.10 planar 追蹤要能圈欄，不只圈列

`-vga-trace-rows` 圈列，`-vga-trace-cols` 圈位元組欄（一欄八像素）。
只圈列常常不夠：同一列上面畫的東西可能來自好幾個呼叫，而環狀緩衝只留
最後四十筆——要找的那一筆通常在中間。

> 源平合戰的「決定」鈕：圈第 321–339 列拿到的四十筆全是右邊界的框線，
> 加上 `-vga-trace-cols 45-49` 才看得到畫按鈕的那支常式（`035F:3E8A`），
> 從那裡往回追才找到畫布原點那對全域變數。

## 4.11 `-call-args` 要印呼叫端是誰

同一支輔助常式在一次繪圖裡會被叫上百次，光看參數分不出哪一次屬於哪個
元素。`-call-args` 的每一列現在都帶**返回位址**（遠呼叫的返回位址就在
`SS:SP` 那四個位元組），`由 CS:IP` 一眼就分得出來。

## 4.12 `-frame-args`：位址在 prologue 之後時從 `SS:BP+6` 取

反組譯給的位址通常是函式中間那幾行（`mov bx,[bp+06]`），不是進入點。
`-call-args` 從 `SS:SP+4` 取，只有停在進入點才對；`-frame-args` 改從
`SS:BP+6` 取，直接把反組譯上看到的位址填進去就好，不必回頭猜
`push bp` 在哪一個 byte。

> 源平合戰的繪圖進入點 `2A1E:5A8B` 就是這種情形。用它把一次對話框重畫的
> 一萬四千次繪圖呼叫的座標全部印出來，才看出值框整批畫在錯的 y。

## 4.13 `-watch` 印最後 200 筆

四十筆只夠看「最後誰動了它」，看不到一段建構過程。物件陣列這種一次寫
幾百個欄位的東西要看得到整段，才分得出「誰建的」與「誰改的」。

## 4.14 `-poke`：對拍的局面直接設進去

`-poke 步數:位址=值[:值…]`（位址與值都是十六進位，逗號分隔多組）在指定
步數把線性記憶體改掉。

要對拍哪個局面，就把記憶體寫成那個局面——**不要靠遊戲內的隨機，也不要
一路點進去湊**。前者不決定性，後者慢而且每加一個變因就要重跑一次。

同一組 poke 可以掛在好幾個步數上：程式常常會把資料複製到別的結構裡，
只改一次可能改到已經沒人看的那一份。

> 源平合戰用它解「細部地圖上那 39 筆座標各是哪個據點」：把每個據點的
> 歸屬勢力改成一個顏色不重複的值，畫面上的軍旗顏色就直接把答案講出來，
> 不必去猜。

## 4.15 `-arg-regs`：參數不一定都在堆疊上

繪圖驅動這類用組語寫的介面，常常把座標放堆疊、來源位址放暫存器。
`-arg-regs` 讓 `-call-args`／`-frame-args` 的每一列多印
`AX BX CX DX SI DI ES BP`。

> 源平合戰的軍旗：堆疊上只有 x／y／寬／高與兩個常數，來源的位址不在裡面
> ——第五、六個字看起來像遠指標，指過去卻整片是 0。

## 4.16 `-dump-mem` 可以一次挖好幾段

```
-dump-mem "6B4E0-6BF00:/src/workplace/kao.bin,59F30-5A930:/src/workplace/stk.bin"
```

逗號分隔多段，每段 `<lo>-<hi>:<路徑>`（位址十六進位）。

追一張畫面是怎麼合成的時候，來源緩衝區常常不只一塊——頭像在一段
記憶體、對話框的框線磚在堆疊上。**只能挖一塊的話，第二塊就要重跑一次
整支遊戲**（源平合戰跑到主畫面要五億道指令，一趟數分鐘）。

## 4.17 存檔／讀檔：`-save-state` 與 `-load-state`

```
# 存：跑到 8.47 億道指令時把整台機器寫出來
-save-state "595000000:/src/workplace/ck-main.gz,847000000:/src/workplace/ck-cmd.gz"

# 讀：從那裡接著跑（-exe 不必給）
-load-state /src/workplace/ck-cmd.gz -root /orig -steps 860000000 -clicks "850000000:320:240"
```

**這條擋的是「慢迴圈只能用猜的」。** 源平合戰跑到玩家能下指令的命令面板
要八億五千萬道指令，一趟約八分鐘；每問一個問題重跑一次，一天問不了幾次。
存一次之後，每個實驗從那裡展開——實測 4,000 萬道指令的續跑是 **2.1 秒**，
而且與一路跑下來的畫面**逐位元組相同**。

### 步數一律是絕對值

`-steps`／`-clicks`／`-shots`／`-save-state`／`-poke`／`-keys-at` 的數字
**全部是絕對步數**，讀檔之後**照舊往上累加**，不是「從這裡再跑幾道」。
從一個在 8.47 億道的檢查點接著跑，`-steps 6000000` 的意思是
「跑到第六百萬道為止」——迴圈一道都不會執行。

**這件事不會報錯**：畫面、記憶體、狀態檔照樣 dump 得出來，內容就是
檢查點本身，看起來像「點了沒反應」，很容易跑去改座標。判準是報告
第二行「執行 N 道指令」有沒有往前走，以及「滑鼠輪詢」是不是 0 次。

檔案是 gzip 過的兩段 gob，每段前面有 8 bytes 長度
（`internal/state`）。**兩段都要**：

| 段 | 內容 |
|---|---|
| 機器 | 記憶體、CPU、時鐘（`Steps`／`Ticks`／`portTicks`／`nextIRQ0`）、埠、DAC、四個 plane 與 VGA 暫存器 |
| DOS | 開著的檔（路徑與位置，還原時重開再 seek）、配出去的記憶體區塊與洞、行程堆疊與 PSP、監督佇列、XMS 的 EMB 內容、EMS 的頁與映射 |

⚠ **不能把兩個 gob 直接接在一起**：`gob.Decoder` 會預讀，第一段解完
就已經吃掉第二段的開頭，症狀是第二段報
`unknown type id or corrupted data`。所以每段前面要有長度。

⚠ **漏抄欄位不會報錯。** 還原之後機器看起來完全正常，只是某個時鐘或
某個 plane 停在別的時間點，症狀出現在很後面而且不指向這裡。
`internal/state` 的 round-trip 測試就是釘這件事：存檔前後各跑一段，
比對記憶體與 `Ticks`。

診斷用的紀錄（`Opened`／`Reads`／`Allocs`／`EMSOps`／`ExecLog`／
`Mouse.Polls`…）**不進存檔**——它們是那一趟的觀測紀錄，不是機器狀態。

### 素材目錄跟著狀態檔走

存檔會把 `-root`（`dos.DOS.Root`）一起寫進去，讀檔時還原。`-load-state`
時不必再給 `-root`；真的給了就以命令列為準。

理由是**讀檔之後遊戲還會再開檔**。少了這個欄位，`resolve` 會拿預設的
`.` 去找，之後每一次開檔都失敗——而且**不會有任何錯誤**：DOS 的開檔
服務回失敗，遊戲照樣往下走，緩衝區裡留著上一次的填充值，被當成資料用。
症狀離現場很遠：源平合戰的人物頭像變成整塊剪影，而朝廷場景讓 GRPDRV
的解壓迴圈對著一整片 `0x77` 讀到天荒地老（一億道指令只改了 30 bytes）。
唯一的線索是報告最後一行「找不到的檔」。

舊的狀態檔沒有這個欄位，讀進來是空字串，那時沿用目前這一台的設定。

## 4.18 `clickgrid`：逐格點一次，每格都從同一份狀態展開

```
go run ./cmd/clickgrid -state ck-cmd.gz -root /orig \
    -area 288,48,264,176 -step 16 -hold 2000000 -settle 5000000 -out grid/
```

回報哪一格會改變畫面、變成第幾種畫面，並把每一種畫面各存一張。
也可以用 `-only "x,y;x,y…"` 只點指定的幾個點。

與 `probe -sweep` 的差別是**每一格都重新展開狀態檔**，所以格與格之間
互不影響。`-sweep` 是連續點下去，前一格開的選單會影響後一格，
找互動熱點時讀起來很吃力。

這支工具要有 §4.17 的狀態檔才划算：一格約 0.6 秒（載入 ＋ 七百萬道指令），
而從頭跑到那個畫面要八分鐘。實測源平合戰的命令面板，187 格掃完約兩分鐘，
一次就把五個指令圖示的邊界（畫格 x `368` 起、每格 34 寬）與「中止」
的位置全部量出來。

## 4.19 有些鈕吃「游標已經在上面」這個狀態

`clickgrid -premove N`：先把游標移過去、等遊戲讀了 N 次滑鼠，才按下去。

源平合戰的數量對話框（「いかほど売りますか?」）就是這樣：瞬移到「決定」
上面立刻按，**整個對話框一點反應都沒有**——不是按錯位置，同一個座標
先移過去、讓遊戲讀三次滑鼠再按就進得去。滑桿的箭頭鈕反而瞬移就吃，
所以同一張對話框裡兩種鈕的行為不一樣。

判準：`-premove 0` 掃遍整張對話框 171 格只有箭頭那一格有反應；
`-premove 3` 之後「決定」與「中止」都動了。

**這是「點了沒反應」的第四種成因**，前三種是：點在遊戲沒輪詢的視窗裡
（§4.2）、按住時間太短（§4.5）、按住時間太長（一次穿過好幾層選單，§4.18）。
