# 009 — `int 33h` 的事件處理常式與座標夾制

日期：2026-09-05
狀態：**READY**

---

## 1. 為什麼要做

現在的 `int 33h` 只答不問：`AX=000Ch` 登記的事件處理常式**收下來就放著**，
`AX=0007h`／`0008h` 設的座標範圍**收下來就丟掉**。

兩件事因此不成立：

### 1.1 游標的位置由「遊戲什麼時候輪詢」決定

《臥龍傳》畫面上那隻手是**遊戲自己畫的**，而重畫的時機有兩條路：

- 事件常式（IDA `0x20101`）：位置變了就擦掉舊的、畫新的；
- 輪詢路徑 `sub_20070`（`int 33h AX=3`）＋ `sub_2009A`。

實測一次 4,000 萬道指令的跑分裡，`AX=3` 只被呼叫 **5 次**，
`AX=5` 卻有 **240 萬次**——遊戲絕大多數時候靠事件常式維持游標。
我們不呼叫它，游標就停在遊戲上一次輪詢時看到的地方。

⚠ **這件事在目前的對拍裡看不出來**，因為腳本每次點擊之後都會等到
遊戲輪詢過一次。但「移動游標但不點」與「點在按鈕上但畫面還沒重畫」
這兩種取樣點現在是拍不到的，而**畫面看起來完全正常**。

### 1.2 送超出範圍的座標不會被夾住

遊戲開機時把範圍設成 `0`–`27Fh` × `0`–`18Fh`（640×400，`sub_2002E`）。
真的驅動會把游標夾在範圍內；我們不夾，於是送 `y=500` 的腳本會讓
遊戲讀到 500——**而真機上它會讀到 399**。
兩者的差別在「點在畫面外」這種邊界測試上會整個翻轉結論。

> 臥龍傳專案 `docs/playtest/40` §1.2 記著一個同源的坑：
> 「框外游標被夾到列 0，第二列以後永遠點不到」——**夾制是遊戲行為的一部分**。

## 2. 事件常式的契約

`AX=000Ch`：`ES:DX` ＝ 常式（`retf` 結尾）、`CX` ＝ 事件遮罩。

| 位元 | 事件 |
|---:|---|
| 0 | 游標位置改變 |
| 1／2 | 左鍵按下／放開 |
| 3／4 | 右鍵按下／放開 |
| 5／6 | 中鍵按下／放開 |

呼叫時：`AX` ＝ 這一次的事件遮罩、`BX` ＝ 目前按鍵狀態、
`CX`／`DX` ＝ 游標座標、`SI`／`DI` ＝ 水平／垂直 mickey。

《臥龍傳》登記的遮罩是 `0001h`（只要位置改變），常式在 IDA `0x20101`：

```asm
pushf / cli
cmp cs:byte_20100, 1 / jne 出去      ; 快取不新鮮就不畫
cmp cs:word_200FC, cx / jne 重畫
cmp cs:word_200FE, dx / je  出去      ; 位置沒變就不畫
重畫: sub sp,8 / … / xchg cx,cs:200FC / xchg dx,cs:200FE / call 畫游標 …
出去: sti / popf / lret
```

## 3. 怎麼實作

### 3.1 遠呼叫要能回得來，而且不能弄髒暫存器

真機上這支常式是從驅動的 ISR 裡呼叫的，ISR 會把暫存器全部存起來。
我們插進去的時候一樣要做，否則被打斷的那段程式會**莫名其妙拿到別的
`AX`**——症狀出現在很後面，而且完全不指向滑鼠。

作法與字型服務同一招：在 `StubSeg` 種一個 `int F3h` 當**返回哨兵**。

```
1. 把 CPU 狀態整份存起來（含旗標與 SS:SP）
2. push 返回位址 ＝ StubSeg:mouseRetOff（那裡是 `CD F3`）
3. 設 AX/BX/CX/DX/SI/DI，CS:IP 跳到常式
4. 常式 `retf` → 回到 StubSeg:mouseRetOff → `int F3h`
5. 我們在 `int F3h` 把整份狀態還原
```

⚠ **一次只能有一個回呼在跑。** 回呼還沒回來就再插一次，第二次會把第一次
存的狀態蓋掉，然後兩次都回不到原處。用一個「進行中」旗標擋住，
**而且事件要排隊不要丟**——丟掉的話快速移動的軌跡會少幾格。

### 3.2 只在指令邊界插

與週期遠呼叫同一個位置（`Machine.tick`）。事件是外面注入的，
所以「什麼時候真的送出去」要由機器決定，不是由 `MoveMouse` 決定。

### 3.3 座標夾制

`AX=0007h`／`0008h` 存起來，`MoveMouse`／`AX=0004h` 與事件都先夾。

**遊戲沒設過範圍就不夾。** 真機的驅動一定會夾到模式的範圍，
但我們的座標是測試腳本給的、本來就在範圍內；而「預設值猜錯」會讓
第一個案例（mode 13h）安靜地改變行為。**只在有明確來源時才夾**，
是這一條與「不要憑預設值猜」同一個判準。

## 4. 怎麼驗

| 項目 | 驗收 |
|---|---|
| 遠呼叫回得來 | 單元測試：常式只有一個 `retf`，插進去之後 CPU 要回到原本的 CS:IP，**且八個暫存器與旗標一個都沒變** |
| 排隊 | 回呼進行中再送事件，事件要留著、之後補送 |
| 遮罩 | 遮罩 `0001h` 時按鍵事件不觸發 |
| 夾制 | 設 0–27Fh × 0–18Fh 之後送 `(700, 500)`，`AX=3` 要回 `(639, 399)` |
| 整體 | 《臥龍傳》五格對拍**不得回歸**（`docs/findings/003`）。⚠ 這一項是重點：呼叫事件常式會讓游標多一條重畫路徑，畫錯的話畫面上看得見 |
| 正對照 | **移動游標但不點擊**，畫面要跟著變：舊位置擦掉、新位置畫上。實測兩塊 14×14 的差異（`docs/findings/004` §2）|
| 快照 | 佇列、進行中旗標與週期時鐘都要進快照。漏掉的症狀是「從快照展開之後時鐘不走」，而記憶體與 CPU 全對 |

⚠ **「測試綠」不等於接上了。** 事件常式的呼叫點在 `Machine.tick`，
而單元測試可以直接呼叫注入函式——那樣的話把 `tick` 裡那一行刪掉照樣全綠。
接線要另外測。
