# 007 `.COM` 載入器、鍵盤輸入與觀測工具

狀態：**READY**　　日期：2026-09-05

延伸 `003-machine-and-loader.md`（載入器）與 `004-dos-bios-services.md`（服務層）。
這一份只寫新增的部分。

分層照 `006-layering.md` 的判準：**「換一支 binary 之後，這段程式碼還成立嗎？」**

| 東西 | 落在哪 | 為什麼 |
|---|---|---|
| `.COM` 載入器、`int 16h` 佇列、IRQ1 與埠 `60h`、`TextScreen`、`Find` | 機器層 | 只依賴 DOS／BIOS／IBM PC 的規格，看不到任何特定程式 |
| `cmd/run` | `cmd/` | 吃程式路徑，不認識被跑的是什麼 |
| `package dosgolem`（模組根目錄） | 機器層的對外門面 | `internal/` 跨模組 import 不到；`oracle/` 是觀測層，有自己的取捨（`Click`／`Save`／IDA 位址），不是每個使用端都要 |
| 「怎麼在記憶體裡找 `SYSTEM.PME.86`」「dispatch 目標怎麼判」「p-code 軌跡怎麼取」 | **不在這裡** | 那是某一支 binary 的知識，屬於 `apps/` 或使用端的 repo |

最後一列是這份 spec 最重要的一條。**第一版把那些寫成了 `oracle/psys`**，
與 `oracle/rich2` 是同一個問題；已經整包移到使用端
（[`Parhelion-PME86`](https://github.com/wicanr2/Parhelion-PME86) 的 `oracle/`）。

## 為什麼

`RUN_full.EXE` 是 MZ 執行檔，輸入走 `int 21h AH=3Fh`。這兩件事都不是 DOS 程式的通例：

- `.COM` 沒有檔頭，是 DOS 上更早、更常見的格式。
- 自己接 IRQ1、直接從埠 `60h` 讀掃描碼的程式很多——**BIOS 的 `int 16h` 對它們沒有意義**。

第一個踩到這兩件事的是 1984 年 DOS 版的 UCSD p-System（`PSYSTEM.COM`）。
它是別的專案的 oracle 素材，但**這兩項能力本身與那個程式無關**，
所以做在 `internal/machine` 與 `internal/dos`，不是做成某個程式的特例。

## 1 `.COM` 載入器

1.1 `Machine.LoadCOM(data)` 把整個檔案當映像，載到 `PSPSeg:0100h`。
沒有檔頭、沒有重定位表要處理。

1.2 `CS`、`DS`、`ES`、`SS` 全部指向 `PSPSeg`；`IP = 0100h`；`SP = 0FFFEh`。

1.3 `SS:0FFFEh` 要放一個 0。`.COM` 的收工慣例是 `retn`，
那會取走堆疊頂當位移跳過去——放 0 才會落到 PSP 開頭的 `int 20h`。

1.4 `FreeSeg` 設在 `PSPSeg + 1000h`（也就是整整一個段之後）。
`.COM` 行程名義上擁有整個段，配置區不能落在它自己的空間裡。

1.5 空檔案、或 `0100h + len > 0FFF0h` 的檔案，回錯誤。
**不截斷、不四捨五入**——載進去一半的映像會安靜地跑進垃圾。

## 2 `int 16h` 的按鍵佇列

2.1 `DOS.Keys` 是 `Key{Scan, ASCII}` 的佇列，`DOS.TypeKeys(s)` 排 ASCII（掃描碼填 0）。

2.2 `AH=00h`／`10h`（讀）：佇列有東西就取出一個，`AX = Scan<<8 | ASCII`。

2.3 `AH=01h`／`11h`（查）：有東西就 `ZF=0` 並把 `AX` 填成同樣的值，**不取走**。

2.4 **佇列空的時候行為與原本完全相同**：讀回 `AX=0`，查回 `ZF=1`。
`RUN_full.EXE` 走的是 `int 21h AH=3Fh`，不能因為這個佇列改變它看到的東西。

2.5 `DOS.KeyPolls` 累計 `int 16h` 被問過幾次。
「程式到底有沒有在等鍵盤」看這個數字最快。

## 3 IRQ1 與埠 `60h`

3.1 `Machine.KeyQueue` 是待送的掃描碼（IBM set 1，通碼與斷碼都要自己排）。
`Machine.TypeScan(s)` 把一串字元轉成掃描碼排進去，大寫字母用 Shift 的通碼／斷碼包住。

3.2 `TypeScan` 遇到不認得的字元**回錯誤，不安靜跳過**。
少送一個鍵會讓後面整串輸入錯位，而且從結果完全看不出來。

3.3 `keyTick()` 在每一道指令之前跑（與 `tick()` 並列）。三個條件缺一不可：

- 佇列有東西；
- `IF` 開著；
- **程式自己裝了 `int 09h`**（向量的段不是 `StubSeg`）。

最後一條是關鍵：向量還指著我們的 stub 就表示沒有人會讀掃描碼，
這時送中斷只會讓它消失，而且從外面看不出來鍵去哪了。

3.4 兩次鍵盤中斷至少隔 `KeyIRQEvery` 條指令（預設 `DefaultKeyIRQEvery = 20000`）。
隔太近的話前一個掃描碼還沒被處理常式讀走就被蓋掉。
這個值只要求「處理常式來得及跑完」，不模擬真實打字速度。

3.5 埠 `60h` 讀出目前的掃描碼。`In8` 原本對未知埠回 `0FFh`，
那會讓處理常式讀到一個永遠不變的假鍵。

3.6 `Machine.KeyIRQs` 累計送出去幾次。

## 4 通用的觀測工具

4.1 `Machine.TextScreen(cols)` 把 `B800` 的文字頁讀成 25 列字串。
`cols` 為 0 時用 BDA 記的欄數，不合理就退回 80。非可列印字元換成空白；
**空白列保留**——第幾列有東西本身是資訊。

4.2 `Machine.Find(pattern)` 掃整個位址空間回傳所有命中的實體位址。
拿來定位「被程式自己搬進記憶體的東西」：那種東西的載入位址靜態看不出來，
挑一段不會被改寫的內容當指紋最直接。空 pattern 回 `nil`——
回「到處都是」比回「找不到」更難查。

4.3 `Machine.SegmentBytes(seg, n)` 讀一個段開頭的 n 個位元組。
差分比對常要把「原版此刻某個段的內容」整塊拿出來對拍；逐 byte 呼叫 `Read8`
也做得到，但那會讓呼叫端自己算線性位址，而算錯的症狀是
「比對出一堆差異」，不是「報錯」。越界回 `nil`——
回一段補零的東西會被當成「那裡真的是零」。

4.4 **觀測工具**（`internal/machine/probe.go`）。`docs/spec/001` 的 M3 一直掛著
「breakpoint 與 watchpoint 未做」；拿原版當對照的工作沒有它就只能自己寫
逐條 `Step` 的迴圈再輪詢狀態，而**輪詢會漏掉「變過又變回來」**——
那種漏法不會報錯，只會讓某些事件看起來從沒發生過。

| 東西 | 語意 |
|---|---|
| `WatchWrite(lo, hi, on)` | 監看一段位址的每一次位元組寫入。**寫入相同的值也算**——「誰在寫這個位址」與「這個值變了沒」是兩個問題 |
| `WatchWord(addr, on)` | 監看一個 word，**值真的變了**才通知，而且是在一條指令做完之後 |
| `BreakAt(seg, off)` | 執行中斷點，線性位址比對 |
| `RunUntil(stop, budget)` | 跑到條件成立、走到中斷點、或用完預算；回報是哪一種 |
| `Insn()` | 目前這一條指令的**起點** |

4.4.1 `WatchWord` 不在寫入當下通知，因為 16 位元的存放在這台機器上是**兩次位元組
寫入**——當下看會先看到半個新值，那不是任何程式看得到的狀態。

4.4.2 `Insn()` 存在是因為監看點觸發時 `CPU.IP` 已經被解碼推過這條指令了。
「是誰寫的」要問 `Insn`，問 `IP` 拿到的是下一條的位址。

4.4.3 `RunUntil` 的條件與中斷點都在**執行每一條之前**檢查，但**跳過第一條**——
否則停在中斷點上之後再呼叫一次會當場又停下來，永遠走不動。

4.4.4 `StopBudget` 通常表示**條件根本不會成立**，不是「還差一點」。
把預算調大之前先想想為什麼。

4.4.5 沒設任何監看點時，熱路徑只多一次長度檢查。

4.5 `Snapshot` 在對外介面加了型別別名。`Machine.Snapshot()`／`Restore()` 本來就是
公開方法，但回傳的型別在 `internal/` 底下，使用端沒辦法把它放進自己的結構。

4.6 `cmd/run` 是這幾樣東西的命令列外殼：載入 `.COM` 或 `.EXE`、跑一段、
報告缺哪些服務、開過哪些檔、畫面上有什麼、卡在哪個迴圈、以及用指紋定位映像。
**它不認識任何特定的程式。**

## 5 對外介面

5.1 實作分成三層放在 `internal/` 底下，**別的模組 import 不到**。
跨模組要用的東西一律從模組根目錄的 `package dosgolem` 走：
`Machine`、`DOS`、`CPU`、`Key` 是型別別名，加上 `New`、`NewDOS`
與暫存器／旗標／記憶體佈局的常數。

5.2 這一層**只有別名與轉呼叫，沒有邏輯**。加東西進來之前先問一次：
它是「任何 DOS 程式都用得到」，還是「某一個程式才需要」？
後者屬於使用端的 repo。

5.3 `dosgolem_test.go` 從 package 外面走一次最小流程
（造機器 → 載 `.COM` → 掛服務 → 跑 → 讀畫面 → 找指紋）。
少一個別名或常數不會讓內部測試變紅，只會讓使用端編不過——
而那時候通常已經在別的 repo 裡了。

## 6 用它驗證跨段呼叫

第二個案例（DOS 版 UCSD p-System）的 p-machine 有跨段呼叫：一條指令會把整個
程式碼段換掉。要驗「remake 算出來的目標段與原版切過去的那一段相同」，
需要**每一次換段都不漏**。

做法是拿 `WatchWord` 監看直譯器存放「目前是哪一段」的那個 word。
輪詢做不到這件事——兩條 p-code 之間可以換過去又換回來，輪詢只會看到沒變。

`Machine.SegmentBytes` 則讓「我們算出來的那一段」與「原版切過去的那一段」
整塊比對；逐 byte 自己算線性位址很容易錯，而錯的症狀是「一堆差異」不是「報錯」。

## 7 驗收

`internal/machine/loader_test.go`、`keyboard_test.go`、`screen_test.go`、
`internal/dos/keys_test.go` 逐條釘住上面的規則。每一條的反面都不會報錯，
所以判準都寫成「掃描碼有沒有真的送到」「佇列空的時候行為有沒有變」這種可觀察的事。

`tools/ci.sh` 是本機 CI：gofmt（只看本分支動過的檔）、`go vet`、`go test ./...`、
以及 CPU 語料（缺語料就跳過，並且說明跳過不等於通過）。

## 8 已知還沒通的

DOS 版 p-System 收得到 IRQ1，但它的 `int 09h` 處理常式**沒有讀埠 `60h`**，
系統仍停在自己的環狀緩衝區空轉迴圈。那支處理常式還沒反組譯，
所以不知道它實際上從哪裡拿鍵。**這一節寫在這裡是因為它會誤導：
「鍵盤做好了」與「那個程式收得到鍵」是兩件事。**
