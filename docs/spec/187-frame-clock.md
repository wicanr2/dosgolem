# 187 — 幀時鐘：讓「第 N 幀」成為可定址的觀測單位

狀態：**READY**
日期：2026-09-09
動機：rich2 的逐幀對拍（原版與 remake 的同一幀要逐點相同）

---

## 1. 問題

觀測層目前只有兩種時間刻度：**指令數**（`Steps`）與**畫面變化**
（`ScreenIdle`／`Click` 內部的取樣器）。兩種都不是「幀」：

- 指令數與幀沒有固定比例——同一幀裡的指令數取決於那一幀畫了多少東西。
- 「畫面變了」在一幀之內會成立很多次（原版逐塊往 `0xA0000` 寫），
  拿它當幀會**過度取樣**，而且取到的是半畫好的中間狀態。

逐幀對拍需要的是「原版認為自己畫完一幀」的那個時刻。

## 2. 事實：tick 是決定性的

`Machine.Ticks` 是送出去的計時器中斷次數，由 `IRQ0Every`（每幾道指令送一次）
驅動——**不是真實時間**。所以同一組輸入跑出來的 tick 數必然相同，
拿它當刻度不會引入不確定性。這是「幀」能當對拍單位的前提。

⚠ **`IRQ0Every` 改了，幀的長度就改了**。它影響動畫跑多快，
不影響最終停下來的畫面（該欄位自己的說明）。對拍要固定它。

## 3. 兩種幀，不要混用

| | 是什麼 | 誰知道 | 用來做什麼 |
|---|---|---|---|
| **螢幕幀** | VGA 垂直回掃一次 ＝ 螢幕刷新一次 | **觀測層**（硬體事實）| 錄影、逐幀畫面比對 |
| **動畫幀** | 程式自己畫完一格動畫的一步 | 程式層 | 比對動畫節奏 |

**螢幕幀是通用的**：任何 DOS 程式都有它，不必知道那支程式長什麼樣。
DOSBox 是同樣的做法——`VGA_VerticalTimer` 由時序驅動，每次回掃跑一輪
`RENDER_StartUpdate`…`RENDER_EndUpdate`，而 fps 從 CRTC 暫存器算出來
（`src/hardware/vga_draw.cpp`：`fps = oscclock/(vtotal*htotal)`，
mode 13h 的標準值 `vga_fps = 70`）。

⚠ **不要拿程式的位址當通用的幀。** rich2 的像素幀在 `0x1DD76`，
那個數字只對《大富翁2》成立；換一支程式就要重新反組譯，
而且不反組譯就不知道自己取錯了。

rich2 的一個像素幀等 4 個 PIT tick ≈ **4 次螢幕刷新**（PIT 被設成
70.187 Hz，`rich2/docs/re/154`；VGA 是 70 Hz），所以兩種幀的比例是 1:4。

## 3a. 分層：硬體事實在觀測層，程式知識在程式層

**「一幀是幾個 tick」是程式層的知識**，與 DGROUP 同一類（`docs/spec/006`）：

- 觀測層（`oracle`）只提供硬體事實：現在第幾個 tick、下 n 個 tick 之後、
  每個 tick 回呼。
- 程式層（`apps/*`）定義自己的幀。rich2 的一幀是**原版自己的繪製點**：
  `0x1DD76`（`rich2.FrameWait`）是「這一幀畫完、開始等待」的入口，
  每個像素幀執行一次（`rich2/docs/spec/059`「每個像素幀的等待」＋
  `rich2/docs/re/148` §6，confirmed）。

⚠ **不要用「每 4 個 tick」當幀。** 那 4 是**這一幀等多久**，不是幀的判準——
計時器在非動畫期間照樣走（等輸入、選單、其他動畫），除以 4 會生出一堆
**沒有畫面更新的假幀**。假幀不報錯，只會讓「第 N 幀」整段錯位。

把位址寫進觀測層同樣是錯的：`0x1DD76` 是《大富翁2》的數字。

## 4. API

觀測層（通用，不認識任何程式）：

```go
func (o *Oracle) Frames() uint64          // 螢幕刷新了幾次（VGA 垂直回掃）
func AtFrame(n uint64) Cond               // 跑到第 n 次刷新
func (o *Oracle) OnFrame(f func(*Oracle)) // 每一次刷新都呼叫，nil 取消

func (o *Oracle) Ticks() uint64           // 既有：計時器中斷次數
func AtTick(n uint64) Cond                // 既有：跑到第 n 刻
func (o *Oracle) OnTick(f func(*Oracle))  // 新增：每一刻都呼叫
```

`OnFrame` 掛在 `Machine` 推進垂直回掃那一點（`Machine.SetOnFrame`），
**不看 IF**——回掃是顯示硬體的事實，程式 `cli` 的時候螢幕照樣在掃。

沒有 `Ticks()` 與 `AtTick` 就無法指定相位，那兩支已經在做這件事
（`oracle/run.go`：「同一個 Ticks 就是同一個動畫相位」）。
缺的只有**逐刻回呼**——要在每一幀取一張畫面，用 `RunUntil` 是做不到的，
它只停在條件成立的那一刻。

`OnTick` 掛在 `Machine` 送中斷的那一點上（`Machine.SetOnTick`），
**不是每道指令輪詢**——輪詢的話幀時鐘自己就會變成熱點
（`Position` 那個教訓，2026-09-09：逐指令取樣讓整體慢了 10 倍）。
回呼在 `Ticks++` 之後、`Interrupt(0x08)` 之前，所以看到的畫面是
上一幀畫完的結果。

程式層（`apps/rich2`）：

```go
const FrameWait  = 0x1DD76   // 「這一幀畫完」的位址，幀的判準
const FrameTicks = 4         // 這一幀等幾刻（換算節奏用，不是判準）
func EachFrame(o *oracle.Oracle, f func(*oracle.Oracle)) func()
```

`EachFrame` 走 `OnCall(o.IDA(FrameWait), …)`。`OnCall` 只能加不能移除，
所以取消是把回呼變成 no-op。

## 5. 驗收

1. `Ticks()` 在同一組輸入下可重現（跑兩次相同）。
2. `TickCount(n)` 之後 `Ticks()` 剛好多 n。
3. `OnTick` 的呼叫次數等於同一段內 `Ticks()` 的增量。
4. **主選單期間一幀都不觸發**（計時器照樣走）。這條直接否證「幀 ＝ 每 4 刻」。
5. rich2 走一格時，`EachFrame` 的觸發次數等於該速度檔位的幀數
   （`ds:10A0h` ＝ 2／1／0 → 4／6／8），且每一次的棋子座標位移
   符合 `rich2/docs/spec/059` 的位移表。

第 4、5 條是這份規格存在的理由：**幀數對不上就表示節拍取錯了**，
而取錯的症狀是「畫面看起來都對，只是比對永遠差一點」。

## 6. 實測（2026-09-09，新開局、台灣、玩家 1 從格 5 骰 8 走到 117）

兩條**獨立**的路得到同一個數字，這是節拍取對了的證據：

| 路徑 | 做法 | 結果 |
|---|---|---|
| 螢幕幀 | `cmd/frames` 錄 604 幀，對相鄰幀做畫面差分 | 大範圍重繪 49 次、幀 13–204、**間隔 4 出現 47 次** → 48 個像素幀 |
| 位址節拍 | `EachFrame`（`FrameWait`）數觸發次數 | **48**，每格 6.0 |

對上 `rich2/docs/spec/059` 檔位 1 的「每格 6 幀」與 `rich2/docs/re/097`
「新開局跑檔位 1」。48 × 4 ＝ 192 螢幕幀，實測跨度 191。

### 6.1 差分要看大範圍變化

**移動時整個地圖區都會重繪**——`rich2/docs/re/093` 的標題就是「棋子的逐步
移動動畫**與視窗跟隨**」，視窗跟著棋子捲動，所以一個像素幀的差異是
約 24,000 點（`(107,23)`–`(316,196)`），不是棋子那一小塊。

⚠ **小區塊的變化是別的東西。** 落地之後的買地對話框，Yes／No 在
`(255,107)`–`(267,119)` 每幀閃爍——把它當成棋子移動的話，會得到
「移動段每幀都在變、與規格不符」這個錯誤結論（第一次分析就是這樣錯的）。
