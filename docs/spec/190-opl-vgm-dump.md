# 190：把 OPL 暫存器寫入倒成 VGM

狀態：`READY`

## 1. 為什麼要有這一份

`machine.OPL` 已經是一串 `{Bank, Reg, Val, Step}`——**那已經是樂譜了**，
只是沒有人能播。`cmd/probe -opl-log` 把它印成文字（而且丟掉 `Bank`），
用途是逐筆比對，不是聽。

中間缺的是一個**標準檔案格式**。有了它，原版的 FM 配樂就能離線合成成
音檔，而不必拿 MIDI 去套 General MIDI 音色庫——後者得到的是
「同一首曲子、不同的音源」。

**VGM 是通用的，不是某一款遊戲的東西。** 任何有 AdLib／Sound Blaster
FM 的 DOS 程式都會把音符寫進 `0x388`／`0x389`，所以這一支放共同基礎層
（`internal/vgm`），位址、曲目、遊戲流程一律不進來。判準見
`docs/spec/006-layering`：換一支 binary 之後這段還成立嗎——成立。

## 2. 不做什麼

- **不合成波形。** dosgolem 不內建 OPL 合成器；VGM 是交給外部播放器的
  中介格式。「暫存器串是樂譜、波形是演奏」這條線不動
  （`docs/spec/004-machine` §6）。
- **不偵測循環點。** VGM 的 loop offset 一律寫 0（不循環）。從暫存器串
  反推循環點要猜，而猜錯的循環聽起來只是「接得有點怪」，沒有任何東西
  會開口。要循環由使用端自己標。
- **不補 GD3 標籤。** 曲名、作者這些是 per-binary 的知識，屬於 `apps/`
  或使用端，不屬於編碼器。

## 3. 時間基準：`IRQ0Every × PITHz`

VGM 的延遲單位是 **1/44100 秒**（固定，與輸出取樣率無關）。所以要把
`Step`（第幾道指令）換算成秒。

### 3.1 既有的模型與它的破口

`machine.StepsPerSecond()`（`speaker.go`）回一個常數：

```
DefaultIRQ0Every × PITBaseHz / PITDefaultDivisor
  = 165,000 × 1,193,181.8 / 65,536 ≈ 3.00 M 指令／秒
```

它成立的前提是 **IRQ0Every 跟著 PIT 分頻走**（`recalcIRQ0`）：
程式把分頻改成 d 時 `IRQ0Every = IRQ0Base × d / 65536`，而
`PITHz = PITBaseHz / d`，兩者相乘 d 約掉——**乘積與分頻無關**，
所以寫成常數是對的。

破口在 `IRQ0Pinned`（`docs/spec/016-pit-and-speaker` §3.1）：呼叫端用
`-tick N` 釘死間隔之後，`recalcIRQ0` 不再重算，d 就**不會**被約掉。
logh3 實際跑的就是這一組——遊戲把分頻設成 2048（582.6 Hz）、
腳本釘 `-tick 20000`，真正的機器速度是 `20,000 × 582.6 ≈ 11.65 M`，
而 `StepsPerSecond()` 仍回 3.00 M。**差 3.9 倍。**

⚠ 這個錯誤的長相是「**曲子播得出來，只是慢了將近四倍**」。
沒有任何一個環節會報錯：VGM 合法、播放器正常、音色正確。
所以它不能靠事後聽出來，要在換算的那一行就寫對。

### 3.2 這一版用的換算

```
stepsPerSecond = float64(m.IRQ0Every) × m.PITHz()
```

意義是一句話：**每次計時器中斷走 `IRQ0Every` 道指令，而程式認定
兩次中斷相差 `1/PITHz` 秒。** 兩邊都是機器自己的設定，不是外部標定。

- 沒有釘死時它**等於** `StepsPerSecond()`（上面的約分），所以不是
  另立一套模型，是把既有模型寫成它成立的那個形式。
- 釘死時它跟著呼叫端走，`-tick` 不再安靜地改變曲速。
- `IRQ0Every == 0`（計時器關著）時退回 `StepsPerSecond()`——
  計時器關著的時候沒有別的時間來源，而 FM 音樂幾乎都由計時器驅動，
  所以這種情況下錄到的東西本來就要存疑。

已知限制（要寫進報告，不要假裝沒有）：

- **這是傾印當下的快照**。釘死間隔時程式如果中途改了分頻，乘積會跟著
  變，而這裡只取一個值。不釘死時沒有這個問題（乘積不變）。使用端可以
  用 `-vgm-steps-per-second` 傳自己的值蓋掉。
- **不釘死時它與常數差萬分之幾，不是逐位元相等**：`recalcIRQ0` 算
  `IRQ0Every` 是整數除法（分頻 4096 → `165,000 × 4096 / 65,536 = 10,312.5`
  被截成 10,312）。相對誤差約 `1/IRQ0Every`，分頻愈小愈明顯。
  量化不是分歧——真的分歧會差好幾倍。
- **`IRQ0Clamped > 0` 時它仍然是對的那一個**。間隔被夾到 `MinIRQ0Every`
  表示原版要的中斷率比這台虛擬機跑得動的還快，於是機器內部「變慢」了；
  但程式仍然認定兩次中斷相差 `1/PITHz` 秒，所以按 `IRQ0Every × PITHz`
  換算出來的曲速就是程式要的曲速。拿常數換算反而會錯。

### 3.3 換算成取樣

```
sample(i) = round((Step(i) − Step(0)) × 44100 / stepsPerSecond)
```

以**第一筆寫入**為零點。開機到第一個音符之間的空白不錄進去——
那是載入時間，不是樂曲的一部分，而且它的長度取決於執行器多快。

### 3.4 沒有一起改的：`SpeakerWAV`

`oracle.SpeakerWAV`／`probe -dump-wav`（PC 喇叭的一位元語音）仍然用
`StepsPerSecond()` 那個常數。**刻意不動。**

它換一個時間基準就會吐出不同長度的 WAV，而那是三國演義那條線的產物；
在沒有那邊的收據可以重跑之前改它，等於在別人的專案裡把時間軸改掉而
沒有人會發現。要統一的話是那條線自己的決定，不是這一份的。

這裡登記成**已知的不一致**：同一台機器上，FM 走 `StepsPerSecondNow()`、
喇叭走 `StepsPerSecond()`，釘死間隔時兩者會差幾倍。

## 4. 晶片的選擇

| 條件 | 晶片 | VGM 命令 | 時脈欄位 | 時脈值 |
|---|---|---|---|---|
| 序列裡完全沒有 `Bank == 1` | YM3812（OPL2）| `5A aa dd` | `0x50` | 3,579,545 |
| 出現過 `Bank == 1` | YMF262（OPL3）| `5E`／`5F aa dd` | `0x5C` | 14,318,180 |

`Bank` 的來源是埠：0 ＝ `0x388/0x389`，1 ＝ `0x38A/0x38B`
（`machine.OPLWrite`）。

⚠ **判準是「有沒有寫過第二組」，不是「有沒有開 NEW 位元」。**
只用 OPL2 功能但摸過第二組的程式會被判成 OPL3——那不影響聲音
（YMF262 對第一組是 OPL2 相容的），只影響檔頭上的晶片名。
反過來把 OPL3 判成 OPL2 會**丟掉一半的寫入**，那會少掉聲部。
兩種誤判的代價不對等，所以寧可往 OPL3 偏。

## 5. 檔案版面

版本寫 `1.51`，資料從 `0x100` 開始（`0x34` 的資料位移欄寫 `0xCC`）。

**不能用「資料接在 0x40」那種精簡版面**：OPL 的時脈欄位在 `0x50`／`0x5C`，
資料從 `0x40` 起就會把它蓋掉。症狀是播放器認不出晶片而**安靜地播出無聲**。

| 位移 | 內容 |
|---|---|
| `0x00` | `"Vgm "` |
| `0x04` | EOF 位移（相對 `0x04`）|
| `0x08` | 版本 `0x00000151` |
| `0x18` | 總取樣數 |
| `0x1C` | 循環位移 ＝ 0（不循環）|
| `0x20` | 循環取樣數 ＝ 0 |
| `0x24` | rate ＝ 0（未指定）|
| `0x34` | 資料位移 ＝ `0xCC`（→ 資料在 `0x100`）|
| `0x50` | YM3812 時脈（OPL2 時填）|
| `0x5C` | YMF262 時脈（OPL3 時填）|
| `0x100` | 資料 |

延遲用三種命令，挑短的：

- `0x70+n`：等 n+1 個取樣（1–16），一個位元組
- `0x61 nnnn`：等 nnnn 個取樣（16 位元小端，≤ 65535），三個位元組
- 超過 65535 就連續發多個 `0x61 FFFF`

結尾一律 `0x66`。

⚠ **沒有 `0x66` 的 VGM 不是短了一點，是整份廢掉**：播放器讀到檔尾
才發現沒有結束標記，多數的反應是把後面的垃圾當成命令。
所以收尾寫在編碼器裡，不交給呼叫端記得。

## 6. 對外介面

```go
// internal/vgm（純的，不認識 machine、不認識任何程式）
type Write struct{ Bank, Reg, Val uint8; Step uint64 }
func Encode(w io.Writer, writes []Write, stepsPerSecond float64) (Stats, error)

// internal/machine
func (m *Machine) StepsPerSecondNow() float64
func (m *Machine) OPLVGM(w io.Writer, stepsPerSecond float64) (vgm.Stats, error)

// oracle
func (o *Oracle) StepsPerSecond() float64
func (o *Oracle) OPLVGM(w io.Writer, stepsPerSecond float64) (vgm.Stats, error)
```

`stepsPerSecond` 傳 0 ＝ 依 §3.2 自己推。

`Stats` 回報寫入筆數、總取樣數、秒數與判到的晶片——**報告要印出來**。
「錄到 0 筆」與「錄到 3 萬筆」在檔案大小上分得出來，但
「曲速差四倍」只有秒數看得出來。

`cmd/probe` 的旗標是 `-dump-vgm <檔>`，與 `-dump-wav`／`-dump-ega`
同一組命名；另外兩支：

| 旗標 | 做什麼 |
|---|---|
| `-vgm-clear-on-open <檔名>` | 開到這個檔時 `ClearOPL()`，把輸出框到那一首上 |
| `-vgm-steps-per-second <數>` | 蓋掉 §3.2 的時間基準（0 ＝ 自己推）|

## 6.1 框曲子只能靠開檔那一刻

一次執行會連放好幾首（開機動畫一首、進遊戲又一首），而**暫存器串是
接起來的**——中間沒有分隔符，事後從序列裡找分界只能用猜的。
`oracle.OnFileOpen` 那段註解講的就是這件事：開檔是唯一的錨。

`-vgm-clear-on-open` 把它接到命令列上。兩個設計選擇：

- **只清序列不清暫存器檔**（`ClearOPL` 的語意）。驅動開機時把預設音色
  灌進全部 18 個 operator，之後的曲子是**疊在那個狀態上**的；連狀態一起
  清會讓後面的序列從一台剛開機的晶片開始，與原版的實際情況不同。
- **給了卻沒開到那個檔就不寫 VGM**。這時錄到的是**別首**——而它照樣
  產出一份聽起來完全正常的音檔，檔名卻寫著這一首。那種錯沒有人會發現，
  所以要在這裡擋住，不能只印個警告。
- **只切第一次開檔**。同一首可能被開第二次（曲子重播一輪），每次都切
  留下的是**最後那一小段**；而那一段照樣合法、照樣播得出來，只是短得
  莫名其妙。「這一首從哪裡開始」的答案是第一次載入。
  （logh3 實例：開頭動畫跑完會重播一輪，`OPEN_M.MDS` 開兩次，
  每次都切的結果是 94 秒變成 7 秒。）

## 7. 錄不到東西時的三個檢查點

`AdLib` 預設**不存在**（`oracle.AdLib`／`probe -adlib`）：偵測失敗的程式
會整段跳過音樂路徑，於是序列是空的。空序列與「這個程式沒有音樂」
長得一模一樣，所以：

1. `-adlib` 有沒有開；
2. 程式有沒有跑到會播音樂的地方（步數夠不夠）；
3. 這一段音樂是不是走 MIDI／MPU-401 而不是 FM（那不會碰 `0x388`）。

編碼器對空序列回錯誤而不是寫出一份 0 筆的 VGM——**一份合法但沒有
音符的檔案會一路通過所有後續步驟**，最後在喇叭上變成「沒聲音」，
而那時候已經離這裡很遠了。
