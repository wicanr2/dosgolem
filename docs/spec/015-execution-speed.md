# 015：執行速度

狀態：`READY`

## 1. 為什麼要有這一份

對拍的每一支測試都要把原版**從開機跑到目標畫面**。智冠《三國演義》
走到主選單約三十億道指令，一支測試因此要一分鐘起跳，而一輪對拍
有八十支。執行速度直接決定「一輪要等多久」，也就決定了敢不敢重跑。

**「慢」要先變成數字才調得動。** 沒有數字的時候分不出兩件事：
這一段本來就有幾十億道指令，還是每道指令太貴。

## 2. 怎麼量

`cmd/probe` 每次跑完印一行：

```
執行 400000000 道指令，耗時 15.939s，25.1 M 道／秒
```

那個數字**只涵蓋執行迴圈**（載入與收尾不算），所以同一支執行檔、
同一個 `-steps`、同一台機器之間可以直接比。

找瓶頸用 `-cpuprofile`：

```sh
tools/go.sh run ./cmd/probe -exe … -steps 400000000 -cpuprofile workplace/p.prof
tools/go.sh tool pprof -top -nodecount=25 workplace/p.prof
```

⚠ **要量對拍真正走的那一條路。** `cmd/probe` 的迴圈與 `oracle.RunUntil`
不同（後者每道指令多一個條件函式與一次 hook 查表），拿 probe 的剖析
去調 oracle 會調錯地方。對拍那一側量法是在使用端下
`go test -cpuprofile`。

## 3. 基準（2026-09-09，智冠《三國演義》`AA.EXE`）

容器 `golang:1.24-bookworm`、`--cpus 2`、單執行緒。

| 路徑 | 速度 |
|---|---|
| `cmd/probe` 迴圈 | 24.9–25.1 M 道／秒 |
| `oracle.RunUntil`（有 hook）| 約 24 M 道／秒 |

剖析（`oracle` 那一側，20.3 秒取樣）：

| 函式 | flat | 是什麼 |
|---|---|---|
| `cpu.execute` | 17.8% | 指令分派與短指令的本體 |
| `machine.Read8` | 11.8% | 每一次記憶體讀取 |
| `oracle.RunUntil` | 8.1% | 每道指令的迴圈開銷 |
| `cpu.fetch8` | 6.4% | 取指令 |
| `cpu.decodeModRM` | 6.1% | |
| `cpu.Step` | 5.6% | 前綴迴圈 |
| `machine.Write8` | 4.7% | |
| `machine.tick` ＋ `keyTick` | 3.8% | 每道指令各呼叫一次 |
| `ega.write` | 1.2% | **畫圖不是瓶頸** |

**畫圖只佔 1.2%。** 平面式 VRAM 的寫入分派比想像中便宜，
「跑得慢」的來源是指令本身的數量與每道指令的固定成本。

## 4. 這一版做的三件事

### 4.1 每道指令的兩個中斷檢查改成內聯的快路徑

`Machine.Step` 原本無條件呼叫 `tick()` 與 `keyTick()`，兩支都在
第一行就 return。函式呼叫本身要錢（兩支合計 3.8%），把「要不要進去」
的判斷提到呼叫端，絕大多數指令連呼叫都不用發。

### 4.2 取指令走直接索引，不走匯流排介面

`CPU.Bus` 是介面，每次 `Read8` 都是一次動態分派。取指令是最頻繁的
記憶體存取（每道指令 1–3 個位元組），而**程式碼不會放在視訊記憶體裡**
——`oracle` 與 `probe` 的迴圈都把 `CS:IP ≥ A0000` 當成致命錯誤。

所以 `CPU.Code` 這個欄位非 nil 時，取指令直接索引那一片線性記憶體。
`Machine` 在建構時把 `m.Mem` 指給它。

⚠ **裝了讀取監看（`WatchReads`）時要關掉快路徑**，否則取指令不會
觸發監看。`Machine.WatchReads` 因此在開監看時把 `CPU.Code` 設成 nil、
關監看時設回去。**取指令要不要算「讀取」是個選擇**，這裡選的是
「算」，因為監看的用途是回答「誰碰了這個位址」，而執行也是一種碰。

### 4.3 `oracle.RunUntil` 的迴圈少算一次位址、少查一次 map

原本每道指令算兩次 `IP().Linear()`（護欄一次、`fireCallHooks` 一次），
而 `fireCallHooks` 是一次 map 查詢。改成算一次位址，再用一張
**1 M 位元的點陣圖**（128 KB）先問「這個位址上有沒有 hook」，
有才查 map。點陣圖只在第一次註冊 hook 時配置。

## 5. 量到的結果

**這台機器同時有別人的容器在跑，單次計時不可信。** 量到過
`load average 21`，同一份執行檔同一個 `-steps` 一次 24.9 M 道／秒、
一次 15.3 M 道／秒——**照單次數字看會得出「改完變慢了 40%」的結論**。
做法是**同一個容器裡交錯跑舊新各三次，取各自最快的一次**：

| | #1 | #2 | #3 | 最快 |
|---|---|---|---|---|
| 舊 | 18.3 | 9.0 | 20.0 | **20.0** |
| 新 | 21.0 | 17.5 | 22.6 | **22.6** |

（M 道／秒，`AA.EXE`、`-steps 250000000`；新的三對都贏。）

**＋13%。** 剖析裡的變化更清楚（`oracle` 那一側，同一支測試前後各一次）：

| 函式 | 改之前 | 改之後 |
|---|---|---|
| `machine.Read8` | 11.8% | **3.4%** |
| `machine.tick` ＋ `keyTick` | 3.8% | 掉出前十四名 |
| `oracle.fireCallHooks` | 1.3% | 掉出前十四名（併進 `RunUntil`）|

`Read8` 從 11.8% 掉到 3.4%，是取指令不再走匯流排介面的直接效果。

## 6. 沒有做的：`cpu.execute` 的分派

`execute` 是一個 `switch { case op == 0x06: … }`——**布林條件的
switch，Go 編成一條 if-else 鏈**，落在後面的 opcode 每次要比上百次。
改成 `switch op { case 0x06: … }` 可以讓編譯器出跳躍表，估計省下
`execute` 那 17.8% 的一半左右。

**這一版不做**，因為 CPU 的驗收判準是 SingleStepTests 全部通過
（`CLAUDE.md`），而那份語料 761 MB、不進版控、要連網抓
（`tools/fetch_cputests.sh`）。沒有語料就改 CPU 核心，等於把
「大部分對」當成通過——而 CPU 的錯不會報錯，只會讓上層在幾百萬道
指令之後畫錯一個像素。
