# 008：阻塞式主控台輸入

狀態：**READY**
日期：2026-09-06
起因：智冠《三國演義》(1991) 兩支主程式 `AA.EXE`／`ASV.EXE`

## 1. 問題

真 DOS 的 `int 21h AH=01h`／`07h`／`08h`（主控台字元輸入）與
`int 16h AH=00h`／`10h`（BIOS 讀鍵）都是**阻塞**的：呼叫一次就停在那裡，
**一道指令都不走**，直到有按鍵為止。

dosgolem 是步進式執行器，停不下來，只能返回一個值。而**返回什麼都是在說謊**：

| 做法 | 說的謊 |
|---|---|
| 不動 `AX` | 把上一次殘留的 `AX` 當成按鍵交出去 |
| 回 `AL=0` | 「有一個 `NUL` 鍵被按下」 |
| 回 `StdinFill` | 「有人按了那個鍵」——最糟，因為它看起來像對的 |

三種都會讓 `while (getch() != X);` 這種寫法變成緊迴圈。

### 量到的後果

《三國演義》的 `AA.EXE` 跑五百萬道指令，其中 **356,873 次**落在 `AH=08h`，
每十四道指令一圈。從外面看是「跑滿指令上限、程式還活著」，
與「跑掛了」「在算很久」**長得一模一樣**。

更麻煩的是下游：那一輪的「開過的檔 0」「`A0000` 全零」「`B8000` 全零」
全部是這個缺陷造成的，卻長得像對遊戲的觀測。
**一個不會停的模型會安靜地產生一整批假零。**

## 2. 決定

阻塞就真的阻塞：**佇列空的時候把 `CS:IP` 退回 `INT` 指令本身**，
讓它在下一步重新執行。

`cpu.Rewind()` 已經存在（`internal/cpu/cpu.go`），退的是 `opCS:opIP`
而不是 `IP − 2`——**前綴會讓指令長度不是 2**，這一點自己算會錯。

### 為什麼是「退回重跑」而不是「停機」

退回重跑的語意與真 DOS 逐項相同：

| | 真 DOS | 退回重跑 | 停機 |
|---|---|---|---|
| 程式往前走 | 不走 | 不走 ✓ | 不走 ✓ |
| 計時器 ISR | 照跑 | 照跑 ✓ | **停** ✗ |
| 背景動畫 | 照播 | 照播 ✓ | **凍住** ✗ |

第二列是關鍵。`cpu.Rewind()` 的註解本來就記著這個坑：模擬器立刻返回的話
主程式會當成輸入結束然後退出，**動畫一格都沒播**。停機會用另一種方式
造成同一個結果——畫面停在按鍵前的那一格，而那一格通常不是要看的東西。

`machine.Step()` 每一步都會先 `tick()`，所以退回重跑時計時器照常推進。

### 附帶的 `Blocked` 旗標

退回重跑不會自己停下來，所以另外給一個旗標讓上層決定要不要停：

- `DOS.Blocked`：目前這一步是不是停在阻塞式輸入上。
  每次成功取到鍵時清掉。
- `DOS.KeyWaits`：累計次數。**這個數字大 ＝ 它在等鍵盤，不是在做事**，
  該餵鍵而不是加大 `-steps`。

上層（probe、oracle）可以在 `Blocked` 為真時停下來、餵鍵、再繼續。

## 3. 範圍

**這一版只動 `int 21h AH=01h`／`07h`／`08h`。**

`int 16h AH=00h`／`10h` 同樣是阻塞式，但它**已經有既有行為**
（佇列空回 `AX=0`），而 `rich2` 會呼叫它 20–40 次。
`AH=01/07/08` 是今天才實作的，**沒有任何既有使用者**，所以可以直接給對的語意。

換 `int 16h` 是另一個決定，要先確認 `rich2` 的 parity 不受影響。**這一版不動它。**

## 4. 介面

```go
// 零值 ＝ 阻塞 ＝ 真 DOS 的語意。要舊的空轉行為才設 true。
d.NonBlockingKeys = false   // 預設

d.Blocked        // 這一步停在阻塞式輸入上
d.KeyWaits       // 累計「佇列空時被要求讀鍵」次數
```

`NonBlockingKeys` 的**零值是對的那一邊**：忘記設的人得到的是真 DOS 的語意，
不是一個安靜說謊的模型。

## 5. 驗收

1. 阻塞時程式**一道指令都不往前走**：`-trace` 應顯示 `CS:IP` 與所有暫存器
   釘在同一個值。
   （量到 2026-09-06：`AA.EXE` 釘在 `06DD:21E5`，`AX=0820` 全程不變。✓）
2. 餵鍵之後程式應**往前走**：`CS:IP` 離開 `06DD:21xx` 那個區間。
   （量到 2026-09-06：餵八個 `1` 之後 `CS:IP` 到 `06DD:1685`，
   之後跑了約 790 萬道指令的實際工作才再次阻塞。基準是 53,778 道。✓）
3. `rich2` 既有測試全綠——這一版沒動 `int 16h` 與 `AH=3Fh`，不該有影響。
   （量到 2026-09-06：`go test ./...` 全綠。✓）

⚠ **`AH=08h` 的呼叫次數會上升，不是下降。** 退回重跑代表那道 `INT`
每一步都重新執行一次，所以次數 ≈ 阻塞的步數（量到 2,996,222 ／ 3,000,000 步）。
拿呼叫次數當「有沒有改善」的指標會得到相反的結論——
**要看的是程式有沒有往前走，不是服務被呼叫幾次。**

因此上層要有停損：probe 的 `-block-after`（預設 100,000 步）
在連續阻塞這麼多步之後停下來。留那一段是給計時器 ISR 推背景動畫用的，
再跑下去只是把同一道 `INT` 重跑幾百萬次。

## 6. 這一版沒解決的

- `int 16h` 的阻塞語意（§3）。
- `AH=0Ch`（清緩衝後轉呼其他功能）沒實作；目前兩支目標程式都沒呼叫它。
- 「該餵什麼鍵」不在本規格範圍。阻塞模型只保證**不說謊**，
  不保證走得到某個畫面；走得到是 `apps/` 那一層的事。
