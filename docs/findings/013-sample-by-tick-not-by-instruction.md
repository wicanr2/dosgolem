# 013 — 取樣要以「程式自己的節拍」為單位，不是以指令數

日期：2026-09-05
狀態：已用，靠它抓到 remake 的尋路排序錯誤

---

## 1. 指令數不是時間

即時制遊戲的一拍不是固定指令數——畫面上的東西多，同一拍就多花指令。
臥龍傳的戰術戰鬥一拍平均約 333,000 道，但走位期與交戰期差得很遠。

於是「推 20 拍」寫成 `steps:6660000` 只是估計，而**估計會安靜地錯**：
取樣點漂掉之後，兩邊比出來的差異看起來像行為分歧，實際上是時刻不同。

程式自己有一個計數器（`cs:word_1D318`），讀它就好。

## 2. 兩個動作

| 動作 | 做什麼 |
|---|---|
| `ticks:N` | 跑到節拍計數器**推進 N 拍**（`oracle.NewCond` ＋ `RunUntil`）|
| `units:側/隊` | 只印那一隊的八個兵——逐拍取樣時輸出才看得完 |

```go
// AfterTicks 是「節拍推進 n 拍之後」。
func AfterTicks(o *oracle.Oracle, n uint16) oracle.Cond {
    base := Tick(o)          // ★ 基準在**呼叫的當下**取
    return oracle.NewCond(..., func(o *oracle.Oracle) bool {
        return Tick(o)-base >= n
    })
}
```

⚠ **基準不能在條件裡取。** `Cond.ready` 每道指令被問一次；
在裡面取基準等於永遠差 0 拍，第一道指令就成立——
而它會**正常回來、退出碼 0**，只是一步都沒跑。

減法用無號回繞（`Tick(o)-base`），計數器溢位時才不會反過來。

## 3. 它問出了什麼

同一場攻城戰，每 4 拍印一次攻方第 0 隊的八個兵：

| 拍 | 位 2 | 位 3 |
|---:|---|---|
| 12 | (61,29) | (60,34) |
| 16 | (60,31) | (60,34) |
| 20 | **(59,33)** | **(61,34)** |
| 24 | (60,34) | **(62,31)** |
| 28 | (60,34) | (61,28) |

那一隊的陣形是一列縱隊、大將站正中間，而大將是不能對調的。
**兩個兵走出那一欄再走回來**——原版的尋路真的會繞路。

拿這個去比 remake，才發現 remake 的繞路成本從來沒有生效過
（純先進先出之下直線一定先碰到終點）。**一張逐拍的座標表就夠了，
不必反組譯尋路常式。**

## 4. 可以搬去哪

任何「即時制 ＋ 有內部計數器」的程式都適用。
判準是：**程式裡有沒有一個單調遞增、與畫面一致的數**。
有的話就拿它當時間軸，不要拿指令數或牆鐘。
