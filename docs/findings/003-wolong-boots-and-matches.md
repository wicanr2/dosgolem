# 003 — 第二個案例接上來：《臥龍傳》五格逐點與 DOSBox-X 相同

日期：2026-09-05
狀態：通過

---

## 一句話

松崗 DOS/V 版《臥龍傳》的 `KI.EXE` 在 dosgolem 上開機、選劇本、選君主、
進主畫面，**五格畫面對 DOSBox-X 的原版擷取每一區都是 0 個不同像素**。

| 畫面 | banner | command | map | minimap | faction |
|---|---|---|---|---|---|
| `z1-newgame` NEW GAME 確認框 | 0 | 0 | 0 | 0 | 0 |
| `z2-scenario` 劇本選單 | 0 | 0 | 0 | 0 | 0 |
| `z3-leaders` 君主清單 | 0 | 0 | 0 | 0 | 0 |
| `z4-pick` 選定君主 | 0 | 0 | 0 | 0 | 0 |
| `z5-main` 遊戲主畫面 | 0 | 0 | 0 | 0 | 0 |

分區與判定用臥龍傳專案的 `tools/parity_diff.py`（每一區的座標都是從機器碼
算出來的，不是量的）。原版側是同一個專案 `workplace/promo-live/parity-main/`
的唯讀擷取，操作時間軸照抄它的 `capture-metadata.txt`。

**時間**：整條鏈 0.99 秒，3,740 萬道指令。DOSBox-X 那邊同一條時間軸的
`wait` 加起來是 146 秒的牆上時鐘。

## 四個「不會報錯」的坑

這一輪真正花時間的不是寫 VGA，是四個各自安靜失效的東西。
**每一個的症狀都指向別的地方。**

### 1. 沒有字型服務 → 報「記憶體不足」

第一次跑就跑了 330 萬道指令、開了 14 個資料檔，然後
`int 21h AH=4Ch` 帶著離開碼 8 離開。離開碼 8 是 DOS 的「記憶體不足」，
而程式印出來的字串也是 `ERROR: Memory not enougth ! ( at least 560KB )`。

真正的原因在 200 萬道指令之前：`INT 15h AH=50h`（DOS/V 字型服務）
沒實作，遊戲把 `0000:0000` 留在單字元 blitter 的兩條 `call far` 裡，
第一次畫字就是一次遠呼叫到零位址——落點恰好是開機配置記憶體那一段，
於是它重跑一次配置，這一次沒記憶體了。

> **能查出來的唯一理由是指令軌跡。** `-trace` 印出的最後 40 道指令裡
> 有一個從 `0110:F789` 到 `0110:0100` 的突兀遠跳；沒有它的話，
> 離開碼、錯誤訊息與最後那道 `int 21h` 會**一致地**指向記憶體。

### 2. `int 33h AX=5` 的 `BX` 是輸入，不只是輸出

`AX=5`／`AX=6` 問的是「**哪一個鍵**按了幾次」，`BX` 進去是鍵號
（0 左／1 右／2 中），出來才是次數。原本的實作不分鍵。

《臥龍傳》的等待迴圈（IDA `0x121E9`）**先問右鍵**：

```asm
mov ax,5 / mov bx,1 / int 33h   ; 右鍵 → 有就 stc（取消）
mov ax,5 / xor bx,bx / int 33h  ; 左鍵 → 有就讀位置
```

於是每一次左鍵點擊都被右鍵那一問領走，變成「取消」。
畫面上看起來像「點什麼都沒反應」，而每個回傳值單獨看都合法。

### 3. `Click` 拿 `Indexed()` 判斷「畫面有沒有變」

`Indexed()` 讀的是 mode 13h 那塊線性緩衝區。平面模式下那裡**永遠是全 0**，
所以「畫面沒變」恆成立——**每一次點擊都被報成沒反應**，而畫面其實變了。
第一個案例是 mode 13h，所以這一條在它身上永遠不會發生。

### 4. 寫入模式 3 的功能選擇被漏掉

模式 3 不看 Enable Set/Reset（四個平面一律用 Set/Reset），
**但功能選擇（AND／OR／XOR）照常作用**。漏掉這一段的症狀是
**同時出現兩個看起來無關的錯**：

- 君主清單的反白列變成一條純黃色空白條（原版是綠色、字看得見）；
- 同一張圖上捲軸的滑塊不見了。

兩個都來自那一行。單看任何一個都不會指向寫入模式。

## 兩個對上的 40

遊戲設 mode 12h（640×480），但內容只有 640×400、y 原點在第 40 列。
這個 40 有兩個獨立來源：

- **機器碼**：繪製常式的 VRAM 段是 `A0C8h` ＝ `A000h` ＋ `0xC80` bytes
  ＝ 40 列（臥龍傳專案 `docs/re/28` §1）。
- **量測**：`tools/parity_crop.py` 在 DOSBox-X 的 640×480 截圖上找出
  上下第一列有內容的位置，量到偏移 40、高度 400。

dosgolem 這邊把 `Planar()` 出來的 480 列直接量一次，得到 `first 40 last 439
height 400`——第三個來源。

## 視窗座標 → 遊戲座標：分母是 479

DOSBox-X 的視窗是 640×480，`int 33h` 把**整個視窗**等比對映到遊戲的
640×400。舊腳本的 y 要換算回遊戲 y，而換算式是

```
遊戲 y ＝ 視窗 y × 399 ÷ 479
```

不是 `× 400 ÷ 480`。大部分點兩種算法一樣，**只有少數差 1**：
視窗 336 是 279 不是 280。那 1 個像素讓主畫面的游標整塊對不上（62 點），
其餘四區全 0——看起來像「只差一點點」，不像「換算式錯了」。

dosgolem 沒有視窗，送進去的就是遊戲座標；`wolong.FromDOSBoxY` 只是為了
讓既有的 DOSBox 腳本搬得過來。

## 即時制：日期是問得到的，不必猜秒數

這一款是即時制，同一串操作在牆上時鐘的不同時刻會停在不同的遊戲日期。
DOSBox 那邊只能寫 `wait:3` 之類的秒數去逼近，猜錯就是「畫面差了幾天」，
而那看起來像版面不對——臥龍傳專案 `docs/playtest/39` 的原版擷取停在
4 月 9 日、remake 停在 4 月 1 日，那 158 個不同像素其實是日期。

在這裡日期是**問得到的**（`ds:0CF0`／`0CF4`／`0CF6`，臥龍傳專案
`docs/re/06`），所以取樣點可以直接寫成日期：

```
-script "…;until:196/4/9;shot:s1-system"
```

前提是時鐘要真的會走。**它掛在音效驅動上**：`YNSOUND.COM` 用 291.3 Hz
呼叫遊戲登記的回呼（`INT 61h AH=0Ch`），遊戲的整個時間模型建在那個
計數器上。不接這一支的話日期永遠停在第一天，**而畫面完全正常**——
看起來像「遊戲在等玩家操作」。細節與實作在
[`docs/spec/008`](../spec/008-wolong-services.md) §6.1。

## 順手裁決了一個原版的懸案

臥龍傳專案 `docs/re/29` §6 掛著一個未解項：`STR.EXE`（字型服務的 TSR）
寫死的檔名是 `END_S10.DAT`／`END_S11.DAT`，而封裝內的那兩個檔是結局過場圖。

dosgolem 這邊的字型服務把檔名做成參數（預設 `END_S13`／`END_S14`），
所以「照 `STR.EXE` 的字面跑一次」變成一個可執行的實驗。
**這一輪還沒跑那個變體**，但路已經開好了。
