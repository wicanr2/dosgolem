# 001 — 防拷判定在 dosgolem 上總是通過（未解）

日期：2026-09-04
狀態：**不追**（使用者裁決 2026-09-05：「防拷判定可以忽略，我們就是要進入原版
遊戲讓 remake 對拍」）。邊界已量到，根因未定，不再投入。
影響：低——過了就進遊戲，遊戲本體的對拍不受影響

---

## 現象

`cmd/solvepw` 用快照展開四個顏色，三題連過，畫面出現「完全正確／終於可以開始玩了」。
問題是**怎麼點都會過**。

## 量到的邊界

| 實驗 | 結果 |
|---|---|
| 三題都選綠色 | 全過 |
| 三題都選藍色（`-reverse`）| 全過 |
| 不點留白區，改點立繪上的 (250,100)（`-wrong-x/-y`）| 全過 |
| **完全不點，跑 1.4 億道指令** | **畫面完全不動**，還是第一題 |

最後一列很重要：它排除了「換題是計時器驅動的」。**點擊確實有被處理**
——收到點擊就前進，只是**顏色與位置的判定沒生效**。

## 原版的行為

`rich2` 那邊要真的答對：`tools/dosbox_play.py` 拿說明書掃描圖做 IoU 比對挑顏色，
而 `docs/re/000-index.md` 記著答錯的字串
`1BFC9`「答錯一輪，請重新輸入／很抱歉／您可能看錯了密碼／麻煩您重新輸入」。
那條路徑存在，就表示判定會失敗。

## 為什麼不追

防拷是**進遊戲的門**，不是要對拍的內容。過了就進遊戲，之後的畫面、狀態、
亂數序列都不受這一條影響——而那些才是 remake 要比對的東西。
使用者 2026-09-05 明確裁決：忽略它。

留這份文件是因為**它可能是徵兆**：判定「總是相等」的典型成因是比對的兩邊有
一邊是沒填過的記憶體（`docs/spec/004` §1.3：沒建的東西不會抱怨，只會給 0，
而 0 是合法值）。如果將來遊戲裡別的判定也出現「怎麼做都通過」，先回來看這裡。

## 真要查的話怎麼查

按證據強度排：

1. **攔字串繪製點往回追。** 「完全正確」是 IDA 線性 `1C046`
   （`rich2/docs/re/000-index.md`）。用 `oracle.OnCall` 掛在它的呼叫端，
   看是誰決定要印它、判斷條件讀了哪個變數。
2. **記憶體差分。** 在防拷畫面 `Save()`，選綠色點一下、`Restore()`、選藍色點一下，
   比對兩次的 DGROUP。**選的顏色一定存在某處**——找到它，就找到判定的輸入。
3. **對照 DOSBox。** 同一個固定種子版在 DOSBox 上答錯一次，用同樣的方式找
   「答錯」與「答對」在記憶體上的差別。這一步最貴，留到前兩步走不通再做。

⚠ **不要用「多試幾種點法」去逼它出現失敗**。那是抽樣不是實驗
（`~/.claude/rulebook/40-learning-loop.md`）。
