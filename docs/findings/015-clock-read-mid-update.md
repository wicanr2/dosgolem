# 015 — 「日期到了」不能在時鐘更新的中途判定

日期：2026-09-06
狀態：已修，兩個症狀都消失

---

## 1. 兩個症狀，同一個成因

**症狀一**：`until:` 停下來時**永遠是 23 時**。
四月十八號那一輪停在「4月18日 23時」，四月二十號那一輪停在「4月20日 23時」。

**症狀二**（貴得多）：`until:196/5/3` 與 `until:196/5/16`
**停在同一個指令數、同一個「5月30日 23時」**——而那兩個目標差了十三天。

第二個症狀本來很難發現：它不報錯、回傳的日期也長得像個合法日期。
發現它是因為**指令數對不上**——那個數字只夠跑到五月初。

## 2. 成因

遊戲的時鐘是一條逐個欄位寫的進位鏈：時 → 日 → 月 → 年。
條件每道指令檢查一次，所以會看到中途狀態：

| 那一瞬間 | 日 | 時 | 月 |
|---|---|---|---|
| 換日 | 已經進位 | **還沒歸位（23）** | — |
| 換月 | **還停在 30** | 23 | 已經是 5 |

換月那一瞬間的 `(月=5, 日=30)` 讓 `日 >= 3` 與 `日 >= 16` **同時成立**。
兩個不同的目標因此停在同一個地方。

## 3. 修法：只在主迴圈的閒置點取樣

```go
if o.IP().Linear() != idle {   // idle ＝ sub_1E453，主迴圈每一圈叫一次
    return false
}
d := Clock(o)
```

那裡的時鐘一定是自洽的，而且判定成本比每道指令讀四個 byte 低得多。

修好之後：`until:196/4/20` → **4月20日 1時**、`until:196/5/1` → **5月1日 1時**。

## 4. 可以搬去哪

任何「條件建立在多個欄位上」的停止條件。判準：

> **這幾個欄位是同一道指令寫的嗎？** 不是的話，逐指令檢查一定會看到
> 中途狀態，而中途狀態通常仍然是一組**合法的值**——所以不會報錯。

修法一律是「挑一個結構上自洽的取樣點」，不是「多讀幾次取多數決」。

⚠ 同一個形狀的另一半：**用單一欄位當條件就沒有這個問題**。
`ticks:N`（讀節拍計數器）與 `runto:`（比 CS:IP）都是單一值，天生自洽。
