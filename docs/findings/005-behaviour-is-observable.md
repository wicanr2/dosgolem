## 2. ⚠ 視窗座標 → 遊戲座標：x 不是永遠 1:1

`z6` 的最後一次點擊在視窗 `(416, 19)`。照 `docs/findings/003` §「分母 479」
換算 y 得 15，x 照舊 416——量出來 `banner` 差 62 點，
而那 62 點是**游標整塊往右一格**：原版的游標在 `x=415`，我們在 `x=416`。
把最後一點改成 `(415, 15)` 就回到 0 px。

但同一批裡 `300`／`360`／`450` 三個 x 都是 1:1 對上的（那三格 0 px）。
**所以不是一條線性換算式**，成因未查。

⇒ 實務規則：**只有游標會受這一點影響**（它是唯一由輸入座標決定位置的
畫面元素）。逐點比對只剩下一塊 14×14 的差異時，先把座標 ±1 試一次，
不要當成版面缺陷去追。

## 3. 行為問得到了

`-watch <IDA 線性位址>` 掛在原版的任一支常式上，進去的時候印暫存器與呼叫端。
拿遊戲時鐘的推進常式 `sub_11D8E` 當正對照：

```
#42769657 呼叫 11D8E AX=0110 BX=0101 … 來自 近=11D1F 遠=2D26F
#42809486 呼叫 11D8E AX=0110 BX=00DA … 來自 近=11D1F 遠=2D26F
#42834400 呼叫 11D8E AX=0110 BX=00F6 … 來自 近=11D1F 遠=2D26F
```

間隔約 **24,900 道指令**＝一個子刻。一個遊戲日 216 子刻 ⇒ 538 萬道指令，
與 `docs/findings/003` 量到的「約 500 萬道指令一個遊戲日」對得上——
**兩個獨立的量法給同一個數字**。

⚠ **`near` 與 `far` 的返回位址在堆疊上的版面不同**，挑一種安靜地印會讓
另一種讀到垃圾，而垃圾看起來就是一個合法位址。所以兩種都印。
上面那一行的 `近=11D1F` 對得上反組譯（`sub_11D8E` 的呼叫端），
`遠=2D26F` 是同一份資料的錯誤讀法——留著是為了讓人看得出來哪一個合理。

同一輪也補上 `peek:OFF:N`（讀 `ds:` 的位元組）。正對照：

```
   ds:0CF0 = 01 1E 00 01 04 00 C4 00      ← 日 01、該月 1Eh 天、子刻 00、
   遊戲時鐘：196年4月1日 1時                  時 01、月 04、年 00C4 ＝ 196
```

同一份資料兩條路（讀記憶體 vs. 讀畫面上的日期）給同一個答案。

## 4. 這打開了什麼

畫面對拍只回答「長得一不一樣」。行為對拍要問的是「原版在這一步**算出**
什麼」，而那在 DOSBox 那條路上只能從像素反推。現在三件事都問得到：

- **狀態**：`peek` 任何 `ds:` 欄位（日期、資金、兵力、AI 旗標…）。
- **控制流**：`-watch` 任一支常式，看它什麼時候被呼叫、參數是什麼、誰呼叫的。
- **時間**：`until:Y/M/D` 直接把取樣點寫成遊戲日期。

戰術畫面與 AI 行為因此不再需要「猜一個等待秒數再截圖」——
**取樣點可以寫成條件**，而條件可以是原版自己的變數。
