# 004 — 字型來源做成參數之後，順手裁決了一個原版懸案

日期：2026-09-05
狀態：通過

---

## 1. 兩件事

- `INT 15h AH=50h` 要讀哪個字模檔變成參數（`oracle.Options.FontFull`／`FontHalf`）。
- `int 33h` 的事件處理常式**真的呼叫了**（`docs/spec/009`），座標也會夾。

第二件的正對照在 §2，第一件的實驗在 §3。

## 2. 正對照：移動游標但不點擊，畫面要跟著變

《臥龍傳》畫面上那隻手是遊戲自己畫的，重畫有兩條路：事件常式與輪詢。
實測一次四千萬道指令的跑分裡 `int 33h AX=3` 只有 **5 次**，
`AX=5` 有 **240 萬次**——游標幾乎全靠事件常式。

接上之後，開機、`move:120,90`、再跑 20 萬道指令，兩張畫面的差異是：

```
區塊 y  90..103  x 120..133（93 點）   ← 新位置畫上
區塊 y 200..213  x 320..333（95 點）   ← 舊位置擦掉
```

兩塊 14×14，正是游標。**接上之前這一步一個像素都不會動**，
而畫面看起來完全正常——只是游標留在遊戲上一次輪詢時看到的地方。

五格對拍**沒有回歸**（25 個比較仍然全部 0 px）。

## 3. 實驗：照 `STR.EXE` 的字面跑一次

臥龍傳專案 `docs/re/29` §6 掛著一個未解項：DOS/V 字型服務的常駐程式
`STR.EXE` 寫死的檔名是 `END_S10.DAT`／`END_S11.DAT`，
而封裝內的那兩個檔看起來是結局過場圖。兩個方向都說得通：
安裝流程會改名，或者 `STR.EXE` 與資料檔不同步。

字型來源變成參數之後，這變成一行指令：

```sh
go run ./apps/wolong/cmd/shot -exe KI.EXE -root <原版目錄> \
    -font-full END_S10.DAT -font-half END_S11.DAT \
    -script "wait;click:320,179;wait;click:300,158;wait;shot:s10-leaders"
```

結果：**216 次取字模裡有 68 次超出檔尾**，畫出來的中文是一片雜訊
（數字仍然正常——那是遊戲自己的 8×16 點陣字，不走字型服務）。

所以「照封裝內的檔案跑 `STR.EXE`」這條路是**確定不成立**的。
剩下的兩個假說都還在，但至少「出貨的這一份可以直接這樣跑」被排除了。

⚠ **這一項要小心不要多說。** 這個實驗證明的是
「**這一份封裝裡的** `END_S10/S11` 不是字模」，不是「`STR.EXE` 有 bug」——
安裝流程如果會改名，安裝後的目錄仍然可能是對的。

## 4. ⭐ 順帶發現：對拍的基準畫面根本沒有載 `STR.EXE`

臥龍傳專案的 DOSBox-X 擷取腳本開機只跑三支：
`YNFONT.EXE`、`YNSOUND.COM`、`KI.EXE`——**沒有 `STR.EXE`**。

而封裝內只有 `STR.EXE` 會掛 `INT 15h` 向量（`mov ax,2515h` 兩處）；
`YNFONT.EXE` 一次都沒有，也沒有任何常駐呼叫。
`KI.EXE` 那一側**沒有 fallback**：拿不到向量就是 `call far 0000:0000`
（`docs/re/29` §2，confirmed）。

⇒ 那份基準畫面裡的中文，是 **DOSBox-X 自己的 DOS/V 字型服務**畫的。

而我們用 `END_S13.DAT` 畫出來的 108 個字，與那份基準**逐像素相同**。
兩個獨立的字型來源在這 108 個字上完全一致，這是對
「索引式對不對」與「`END_S13` 是不是那份字模」最硬的一次交叉驗證——
比拿 `END_S13` 去比 `stdfont.15` 更有力，因為那是同一份資料的兩種切法。

## 5. 未解

| 項目 | 現況 |
|---|---|
| 半形字模 | 到目前為止**一次都沒被叫到**（每次跑分都是 0 次）。數字走遊戲自己的 8×16 點陣字；半形服務可能只在某些畫面用到，也可能整支是死路 |
| `STR.EXE` 的檔名 | §3 只排除了一個方向。要裁決得看 `INSTALL.EXE` 到底把哪個檔複製成什麼 |
| DOSBox-X 的字型從哪來 | §4 的推論只到「不是封裝裡的東西」。它與 `END_S13` 逐像素相同是事實，來源沒查 |
