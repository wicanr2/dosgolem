# 016 — 長跑要快，先問「指令花在哪」，不要猜

日期：2026-09-06
狀態：已用，同一段遊戲時間 9,500 萬道 → 2,600 萬道，狀態軌跡逐欄相同

---

## 1. 問題

即時制遊戲當 oracle，一個遊戲日要**五百萬到一千萬道指令**。
想看 AI 三個月的行為就是十億道，跑一次要很久。

**誘惑是「算好結果直接改狀態」**——那會毀掉 oracle：
答案就變成我們自己算的，而 oracle 存在的唯一理由是「答案是原版算的」。
要加速就得加速在**跑得更快**，不是**跳過計算**。

## 2. 先量：取樣式剖析器

`profile:N[,每幾道取樣][,分段大小]` 跑 N 道指令，
定期取樣 CS:IP，印出最熱的幾段。

第一輪（大地圖閒置）：

```
1D600–1D6FF   57.79%     ← sub_1D66A 把 40×23 顯示清單搬進 VRAM
1D700–1D7FF   26.34%
1D800–1D8FF    3.78%
```

**88% 在繪圖底層。** 於是把那兩支的入口塞 `retn`（`nodraw`）——
結果只快了 17%。

## 3. ⚠ 省下來的被別處吸收了

關掉繪圖之後再剖析一次，熱點整個換人：

```
11E00–11E0F   60.75%
11DF0–11DFF   16.01%
```

那是 `sub_11D8E`（時鐘）尾端的**兩個忙等迴圈**：

```asm
mov al, ds:0CFAh              ; 戰略速度設定值
and al, al / jz  .ret         ; 0 ＝ 不等待
.wait1: cmp byte ptr ds:0D2Ch, 0 / jz .wait1
.wait2: cmp ds:0D2Dh, al        / jb .wait2
```

⭐ **繪圖與等待是可互換的**：每一圈的總時間由計時器決定，
繪圖砍掉之後就多等一會兒。所以單獨關繪圖幾乎白做，
單獨把速度設 0（`speed:0`）也幾乎白做（省 0.04%）——
**兩個一起關才有數量級的差別**。

## 4. 結果

同一份存檔跑同樣的 15 個遊戲日（196年4月16日 → 5月1日）：

| 設定 | 指令數 | 倍率 |
|---|---:|---:|
| 原樣 | 79.3 M | 1.0× |
| 只 `nodraw` | 63.4 M | 1.25× |
| 只 `speed:0` | 79.3 M | 1.0× |
| **`nodraw` ＋ `speed:0`** | **10.3 M** | **7.7×** |

⭐ `speed:0` 不是外掛，是**遊戲自己的設定**——系統選單第四列「戰略速度」
的最高速那一格（`ds:0CFA`）。說明書講的「速度超過機器速度時設再快
也不會更快」就是那兩個忙等迴圈。

## 5. ⭐⭐ 加速一定要證明軌跡沒變

「快了」而「答案變了」的加速比慢還糟，而且**不會報錯**。

驗法是現成的：跑到同一個遊戲時刻，把勢力表／據點表／武將表
逐欄比（臥龍傳專案 `tools/state_diff.py`）。

> 5,502 個欄位，**零差異**。

理由也講得通：忙等只燒時間、繪圖只寫 VRAM，
兩者都不在邏輯的因果鏈上；而**每個遊戲小時的主迴圈圈數是固定的**
（`sub_11D8E` 每圈推一個子刻、八個子刻一小時），
所以亂數的消耗序列也不變。

## 5.1 ⛔ 加速解不掉的那一半

上表的 7.7× 量在**和平期**。宣戰之後畫面上的東西變多，
同一組設定只剩約 **2×**。

而真正的天花板不是速度：跑到 196年5月26日 2時，
畫面上是「呂布的兵馬，向許昌進攻過來了！！」——
許昌是玩家的首都，**原版正確地停下來等玩家**，
再推兩億道指令日期一動也不動。

⇒ **先確認「跑不完」是慢還是停。** 兩者的修法完全不同，
而在 log 上長得一樣（都是「跑滿預算仍未達成」）。
判準很便宜：**再推一段，看時鐘動不動。**

## 6. 可以搬去哪

三步，順序不能換：

1. **量**（`profile:`）——不要猜熱點。第一名常常不是你以為的那個。
2. **關掉最熱的那一段之後再量一次**——省下的時間會被別處吸收，
   單獨關一個往往白做。
3. **用既有的對拍證明軌跡沒變**——加速的驗收標準跟移植是同一個。
