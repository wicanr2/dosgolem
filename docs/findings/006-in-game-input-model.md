# 006 — 進到遊戲之後，畫面座標不等於滑鼠座標

日期：2026-09-05
狀態：已解，並用它載入原版存檔跑到系統選單

---

## 1. 症狀

開機到選劇本那一段，送畫面座標就能點中東西（六格對拍全部 0 px）。
**進到遊戲之後同一招失效**：送 (352,15) 想按橫幅的圖示，游標不會到那裡，
**地圖反而捲走了**——而畫面看起來完全正常，地圖本來就會捲。

## 2. 兩個工具把它問了出來

### 2.1 熱區圖：那裡到底有沒有東西可點

`sub_1E453` 用 `offset = (x >> 3) + 10 × (y & 0xF8)` 查一張
**80×50 格、每格 8×8 像素**的熱區圖（臥龍傳專案 `docs/re/22` §2）。
圖的段與偏移在 `ds:E479`／`ds:E47B`，所以整張圖讀得出來：

```
LOAD DATA 畫面：
  #  4  x 432..463  y   0.. 31   ← 系統開關（與 docs/playtest/39 記的一致）
  # 31  x  96..399  y  80..319   ← 視窗本體
  # 32  x 256..375  y 144..159   ← 存檔格 1
  # 33  x 256..375  y 192..207   ← 存檔格 2 …
```

第一次點存檔格點不中，是因為送的 x 是 250 而熱區從 **256** 才開始。
**「點了沒反應」從此不必一格一格試**——一次跑分就把可點的範圍全列出來。

### 2.2 攔 `sub_1E453`：遊戲拿到的座標是多少

選單畫面上，攔到的 `CX/DX` 與我們送的座標**一模一樣**。
進到遊戲之後，同一個攔截點永遠是 `CX=0 DX=0`——包括按下的那一次
（`BX=1` ＝ 左鍵）。所以點擊有被看到，**位置沒有**。

## 3. 成因：捲動原點

`sub_11F7F`（IDA `0x11F7F`）→ `loc_11FD0`：

```asm
word_1987E = cx ; word_19880 = dx      ; 記下原始游標
cx -= word_19882                        ; ← 減掉捲動原點 X
jb  → word_19882 += cx ; cx = 0         ;   變負：原點跟著搬，游標貼邊
cmp cx, 27Fh / jb →
    cx -= 27Fh ; word_19882 += cx ; cx = 27Fh
dx -= word_19884                        ; ← Y 同理，上限 18Fh
word_19886 = cx ; word_19888 = dx       ; ← 這才是畫面座標
```

也就是

```
畫面座標 ＝ 滑鼠座標 − 捲動原點        （夾在 0..27Fh × 0..18Fh）
推到負的 → 原點跟著減、游標貼到 0、**地圖往那個方向捲**
```

**這是遊戲自己實作的「游標推到邊緣就捲地圖」**，選單畫面不走這一層
（那邊 `sub_121E7` 直接拿原始游標查熱區）。⇒ **同一個座標在兩種畫面
代表不同的東西**，而兩邊都不會報錯。

順帶解釋了臥龍傳專案那些看不懂的擷取腳本：`click:0,0` 之後接
`click:37,0` —— 前者把原點推回 0，後者才是畫面座標。

## 4. 作法

`apps/wolong` 補三支：`ScrollOrigin`／`ScreenCursor` 讀值，
`HomeCursor` 把原點歸零（就是遊戲自己的規則：把滑鼠推到 (0,0)），
`ClickScreen`／`TapScreen` ＝ 歸零之後再點。
`cmd/shot` 對應的動作是 `sclick`／`stap`／`origin`。

⚠ **`HomeCursor` 會捲動地圖**，不是無副作用的。要保持地圖位置就自己
記下原點再捲回去。

## 5. 拿它做的事：載入原版存檔，跑到系統選單

```
wait                          開機
click:320,200                 NEW GAME → NO（＝ LOAD DATA）
click:300,151                 存檔格 1（熱區 #32）
sclick:448,15                 系統開關（熱區 #4）
click:376,160                 資料儲存 → SAVE DATA
rclick:150,166                右鍵取消
```

對臥龍傳專案的原版擷取 `parity-load2/u0-sys.png`（**同一份 `SAVE.DAT`**）：

| 區 | 不同像素 | 判定 |
|---|---:|---|
| `banner` | 0 | PASS |
| `command` | 0 | PASS |
| `minimap` | 0 | PASS |
| `map` | 95 | NEAR |
| `faction` | 340 | FAIL |

剩下的 435 點是**時序漂移**，不是繪圖缺陷。兩件事支持：

1. 系統選單開著時畫面**完全凍結**——同一個局面多跑四百萬道指令，
   五區 0 px。所以我們這一側不是「還沒畫完」。
2. 把到達路徑多跑 **60 萬道指令**（約三個遊戲小時），
   同樣的取樣點差 **5,013 點**。435 點對應的時間差比那小一個量級。

差異全部落在右下角，是隨時間變的地圖物件。

## 6. 順帶關掉一個未解

`docs/findings/004` §5 記著「半形字模到目前為止一次都沒被叫到」。
SAVE DATA 視窗把它叫出來了：**全形 304 次、半形 44 次，讀不到字模 0 次**。

## 7. 未解

| 項目 | 現況 |
|---|---|
| 那 435 點的時間差是多少 | 只知道「比 60 萬道指令小一個量級」。要更準得先做「跑到某個 tick」的取樣點 |
| 走到戰術畫面 | 輸入模型解了，路還沒走。要先用熱區圖把「軍團 → 出兵」那條路列出來 |
| `wait` 在遊戲中不適用 | 即時制的畫面永遠不會靜止，`wait` 會一路跑到預算上限（實測跑掉兩個遊戲日）。**遊戲中要用 `steps:` 或 `until:`** |
